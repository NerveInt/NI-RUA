# Unified Action Interface and Program Review

Model tool entry points for new runs are managed by `runtime/tools/definitions.py` and `builtins.py` through `ToolRegistry` (the legacy `tool_catalog.py` has been removed). Task planning, action compilation, physical execution, model presentation, and operational memory are decoupled, while robot state and raw execution evidence remain owned by `Harness` and `Store`.

## Module Responsibilities

| Module | Responsibility |
| --- | --- |
| `actor_instructions.py` / `startup_grounding.py` / `definitions.py`, `builtins.py` | Centralize launch instructions, inline startup `obs_1` 3D grounding (`cam_head` RGB + `obs3d`), public tool declarations, and concise descriptions; legacy tools are excluded from the model catalog. |
| `task_planning.py` | Plain-text task plan, replaceable attention checklist, and evidence ledger; gates the first physical action (submittable standalone or atomically via `robot_action.plan_update`); updating the plan never mutates already compiled trajectories. |
| `codex.py` / `model_proxy.py` | Keep standard `/responses` requests as strict prefix extensions of conversation history (applying only public-boundary filtering and deterministic exact-image deduplication); strip prior Harness snapshots and inject the full current plan snapshot only during primary-actor `/responses/compact` compaction requests. Auxiliary visual review models never receive the episode plan. |
| `unified_actions.py` / `grasp_preview_3d.py` | `robot_action` argument validation, short plan IDs, `preflight` / `execute_if_clean` / `preview` / `execute` / `direct` / `inspect` modes, decoupled `blocking_risks` vs. `advisory_notes`, and `image_delivery` feedback routing. |
| `vectorized_grasp.py` / `pointcloud_field.py` | Batch NumPy vectorized 3D grasp/OBB collision evaluation (`PointCloudSpatialField`), checking both table neighbors and voxel point-cloud clearance without hidden task state. |
| `process_rollout_tracker.py` / `compact_trajectory_summary.py` | 4D `process_trajectory` tracking (`co_motion` fingertip optical flow, closed-jaw `slip_detected`, `in_place_motion` in `deg`/`m`, `event_keyframes`), `object_state_delta` (with optional workspace-wide persistent IDs when `features.persistent_object_tracking=true`), and single-panel `640×480` diagnostic trajectory overlays (`trajectory_overlay.py`). |
| `batch_contract.py` / `batch_motion.py` | Native batch protocol, dependency graph, whole-batch compilation, shared timeline, cached trajectory execution, and observation checkpoint resumption. |
| `batch_geometry.py` | Clearance estimation using the public robot model, caller-supplied obstacles, and held-object bounding boxes; never reads hidden task state. |
| `programs.py` / `program_review.py` | Isolated Python processes, primary-model action review, cancellation and active-work timing, and trusted action result aggregation. |
| `stability.py` | Opt-in bounded visible-motion settling detection that consumes real native steps via standard wait actions. |
| `actor_output.py` / `actor_presentation.py` | Model-facing field compaction, reversible short IDs, and artifact references; raw archived evidence is never mutated. |
| `operation_memory.py` | Separate storage and retrieval for current-task vs. cross-task operational experience, extracting action facts from verified history. |

## From Task Understanding to Execution

Robot capabilities are delivered automatically at launch, and when `features.startup_inline_grounding=true` (the default), the initial scene observation (`obs_1`)—comprising measured robot state, `cam_head` RGB, and inline `obs3d` (`object_table` + `scene3d` handle)—is embedded directly in the opening turn (`ni_rua/cortex/context/startup_grounding.py`, `tests/unit/test_startup_inline_grounding.py`). The model may submit its natural-language task plan either via `task_plan` or atomically inside its first `robot_action(..., plan_update={"plan": ..., "ledger": [...]})` call without an extra round trip:

```json
{
  "plan": "Task goal: transfer the target object as instructed. Approach: select a reachable grasp, transport, and place it. Completion criteria: the target is supported at the destination and remains stable after gripper withdrawal.",
  "attention": [
    {
      "concern": "Whether closing the gripper actually lifts the intended object remains uncertain.",
      "check": "Use feedback from the normal lift stage to verify the object leaves its support and moves with the hand; if not, adjust contact position or grasp orientation.",
      "when": "After lifting and before relying on held-object state for transport."
    }
  ]
}
```

The default operation of `task_plan` is `submit`, which returns a compact confirmation; `update` revises the overall plan or current attention items, and `read` retrieves the full active version. A plan must be submitted before the first physical action (including `robot_wait`). Plans do not need to be updated before every action and are not an instruction table for the motion executor.

We recommend structuring `plan` as a short summary of task goal, approach, and completion criteria. `attention` is an optional list where each item specifies `concern` (current question, hypothesis, or candidate option), `check` (observable verification criteria and how to adjust if violated), and `when` (the action or event that depends on this conclusion). Keep only currently relevant items; items can be added, revised, removed, or paired with operational memories as new evidence arrives. `update` requires at least `plan` or `attention`; omitted fields retain their previous values, and `attention: []` explicitly clears the list. Resubmitting identical fields under the same observation returns `status=unchanged` without creating a new revision or duplicate snapshot, whereas resubmitting the same content under a newer observation records the updated observation provenance. Updating replaces the active checklist while keeping older revisions auditable; retained plan text never becomes verified fact simply by being updated. Each text field is capped at 1,600 characters (excess is rejected rather than truncated), with no mandatory item count.

Standard non-compacting `/responses` requests neither append nor mutate decision reminders so each request remains a strict prefix extension of the previous one to maximize prompt-cache hits. Only when context length triggers a primary-thread actor `/responses/compact` request does the proxy re-read the episode's latest plan, revision, full attention list, evidence ledger, and source observations to inject a complete snapshot. `plan_observation_id`, `attention_observation_id`, and `ledger_observation_id` record the observation active when each respective section was last updated (partial updates preserve unchanged provenance, and legacy archives without provenance report `null`); they do not prove the model's judgment is correct. The snapshot is formatted as an assistant message representing the model's own tentative notes, passed through shared metadata filtering, never elevated to `developer` instructions, never sent to auxiliary visual reviewers, and never used to mutate historical tool receipts. At the compaction boundary, prior Harness snapshots are removed and replaced with a single fresh snapshot while preserving ordinary assistant messages; request retries reuse the exact projected payload without re-invoking context hooks. Agent backends other than Codex get no request-body injection: when the session reports that its model may have lost earlier context (native or relay-detected compaction, uncertain tool-reply delivery, resume after an unclean exit) through `AgentSession.on_context_reset`, `Harness.model_context_reset` marks the reminder due and `Harness.handle_tool` appends the same text and snapshot (`task_planning.decision_reminder_text`, after the same metadata filtering) as one extra `inputText` item to the next actor tool response, then clears the flag. A response whose reminder cannot be built is returned unchanged, with its receipt, and the reminder waits for the next response. Codex runs never receive this sideband (`Harness.decision_reminder_channel`).

Verification should piggyback on normal manipulation feedback whenever possible: a purposeful approach, lift, or withdrawal can simultaneously test a hypothesis. Add dedicated probing steps only when existing evidence is insufficient and the answer would change the next action; in multi-stage batches, insert observation checkpoints only when later stages depend on uncertain earlier outcomes. When a program pauses for default action review, control returns to the primary model along with the latest checklist; programs launched with `allow_direct_actions=true` execute without step-by-step model reasoning and must either evaluate computable evidence conditions themselves or return control to the primary model when judgment is required. The checklist never triggers automatic observations, auto-checks items, or dispatches recovery actions on its own.

Although the pinned Codex SDK/CLI `0.160.0` includes a model tool `update_plan` and `turn/plan/updated` progress notifications, its generated client RPC schema provides no plan read/write API, and `thread/read` / `thread/resume` do not expose a recoverable structured checklist. NI-RUA therefore uses Harness's `task_plan` as the single source of truth rather than maintaining a duplicate native to-do mirror. See the [App Server reference](https://www.codex-docs.com/docs/app-server) and [Hooks reference](https://www.codex-docs.com/docs/hooks) (verified against our pinned local version). Regressions live in `test_task_planning`, `test_codex_requests`, and `test_model_proxy`.

Coordinates in the example below must be derived from the current observation. The action language is the same for every robot, but its fields, names and numbers come from the run's [`EmbodimentProfile`](embodiment-profile.md): on ARX X5 a `move` stage accepts either `grasp_position_m + angles_deg` or `link6` `position_m + quaternion_xyzw` in `env_origin` (the two representations cannot be mixed in the same stage); on SO-101 only `position_m + quaternion_xyzw` of `gripper_frame_link` in `so101_base` exists, the arm id is `right`, and fields the robot cannot honour are absent from its schema and refused by name ([SO-101 integration §4.8](so101-integration.md#48-what-so-101-still-refuses-and-why)). The dual-arm example below and the dual-arm paragraphs that follow describe ARX X5.

Stage parameters are declared per `kind` and share field definitions with the compiler. A `move` stage requires `arm` and a complete pose specification; contact reference fields apply only to grasp poses, and setting gripper speed or synchronized timing requires `gripper_goal_normalized`. A `gripper` stage requires `arm` and `goal_normalized`. The `reason` field is valid only on `observe` checkpoints and must be a non-blank string. Fields from different stage kinds cannot be mixed, and both actor and program calls validate against the same schema before entering the handler. Quaternion normalization, dependency graphs, backend capabilities, cache validity, and execution budgets remain enforced at their respective domain boundaries.

```python
preview = robot_action(
    observation_id=current_observation,
    stages=[
        dict(id="left_approach", kind="move", arm="left",
             position_m=left_target, quaternion_xyzw=left_orientation),
        dict(id="right_prepare", kind="move", arm="right",
             position_m=right_target, quaternion_xyzw=right_orientation),
        dict(id="check", kind="observe", reason="Verify dual-arm arrival and object alignment"),
        dict(id="close", kind="gripper", arm="left", goal_normalized=0),
    ],
)
# After inspecting cost, trajectory, overlay images, and unknowns in the preview:
result = robot_action(mode="execute", plan_id=preview_plan_id)
# After pausing at the observation checkpoint and verifying live feedback, resume the same plan if still valid:
result = robot_action(mode="execute", plan_id=preview_plan_id)
```

The snippet above illustrates arguments passed by the primary model to the native dynamic tool. Inside Python programs, `NiRuaClient.call` returns `success`, `kind`, `data`, and `contentItems`; read `data` keyed by `kind` (with action receipts at `data.receipt`) rather than parsing status strings from display text. The primary model receives images directly as independent image items without needing a JavaScript wrapper or manual base64 decoding. Preview and historical images from program sub-calls are forwarded automatically by `program_run` and `program_status`—never print base64 image strings to `stdout`.

Stages on the same arm are ordered implicitly, while `depends_on` adds cross-arm dependencies; independent stages on opposite arms execute concurrently. An `observe` stage without `arm` waits for all preceding stages on both arms to complete, whereas specifying `arm` pauses both arms as soon as that arm finishes its preceding stage. Each stage can specify its own speed, and `gripper_motion` on a `move` stage schedules gripper actuation across a fractional window of that move (if omitted, the gripper command runs after arm arrival).

To move both arms simultaneously, place left and right stages into the **same** `robot_action` `stages` list—even if all left-arm stages are listed before all right-arm stages, the two arms still advance in parallel on the shared timeline. The launch instruction to "await tool calls sequentially" governs separate tool invocations, not the two arms within a single batch. Splitting left and right moves into two separate `execute` calls runs them serially; similarly, adding a cross-arm `depends_on` or inserting an `observe` stage without `arm` between them intentionally serializes execution. Add cross-arm dependencies only when a genuine physical precondition exists.

### `mode=reach` and split orientation tolerances (SO-101 profile tags)

Two additions are gated by embodiment `supports` tags ([embodiment-profile.md](embodiment-profile.md#supports-tags)); a profile without the tag renders the historical schema, so ARX X5 is unchanged and refuses the fields by name (`unsupported_capability`).

- `reach` adds `mode=reach` (SO-101, always): inverse kinematics only. `observation_id` (the current observation) and 1 to 16 `stages` (`min(max_stages, stages_per_arm * arms)`) are required. Each stage is a `move` with only `id`, `arm`, `position_m` (m), `quaternion_xyzw` and the tolerance fields; `timeout_s` (s) bounds the whole query. Each pose is solved independently from the joints measured at the call (not chained like a preview), every stage is answered even after an unreachable one (its `tolerances` are the IK acceptance bounds only: no arrival-correction, window or stall-guard keys), and nothing is planned, cached, executed or invalidated. Other fields (speeds, jaw goals, guards, `depends_on`, obstacles, `settle`, `plan_update`, `auto_execute_if_clean`, continuation fields) are refused with `robot_action_reach_has_unsupported_fields` or `robot_action_reach_accepts_move_poses_only`; a robot backend without a `reach_batch` method answers `robot_action_reach_unavailable`, and a reach during an in-flight action `robot_action_reach_requires_idle_active_run`. Implementation: `unified_actions._reach`, `RobotBackend.reach_batch`, `SO101Adapter.reach_batch`. The result (`output_contracts.REACH`) has `status` `"solved"`, `stage_count`, `reachable_stage_count`, `physics_advanced` (false), `executed_native_steps` (0) and `stage_results[<id>]` with `ok`, `ik` (residuals in m and rad), `tolerances`, `reached` (`position_m`, `quaternion_xyzw`, `approach_axis` of the planned or closest joints) and, when `ok`, `q_rad` and `joint_travel_rad` (rad). A whole-query failure such as `ik_service_unreachable` is a tool error with that code. Use it to compare candidate grasp, hover and place poses before a preview, which stops at the first failed stage.
- `approach_roll` adds `approach_tolerance_rad` and `roll_tolerance_rad` on move stages and as batch defaults (also accepted by `reach`): `approach_tolerance_rad` is the largest angle (rad, (0, pi], >= 3.14159 = free, default unset) between the achieved and requested approach axis (TCP +Z); `roll_tolerance_rad` is the largest rotation (rad, same range and default) about the approach axis after aligning it, the jaw-direction error. When neither is set orientation is judged as one angle against `orientation_tolerance_rad`; when either is set each component is judged separately and an unset one uses the stage's resolved `orientation_tolerance_rad`. Receipts add `approach_error_rad` and `roll_error_rad`. A tolerance preset sets neither field. SO-101 offers them only with the cuRobo IK service configured; details in [SO-101 integration §12](so101-integration.md#12-ik-planning-the-curobo-ik-service-and-modereach). The fields are carried through `stage_overrides` and repair (`plan_continuation.py`, `batch_repair.py`) like the other tolerance fields.

### Grasp-centre move input (SO-101 pose input `jaw_grasp_centre`)

A profile with the pose input `jaw_grasp_centre` ([embodiment-profile.md](embodiment-profile.md#supports-tags)) accepts, on a `move` stage, the place the centre of the object should occupy between the jaws instead of the TCP position. ARX X5 does not have the tag: its schema is unchanged and it keeps `grasp_position_m` + `angles_deg`, which mean something else (a symmetric gripper with a fixed 0.1501 m offset).

| Field | Unit, range, default | Meaning |
| --- | --- | --- |
| `grasp_centre_m` | [x, y, z] m in `frame_id`; required for this form | Where the centre of the object sits between the jaws. Replaces `position_m` (both together are refused). |
| `object_width_m` | m, [0, `gripper.jaw_grasp.max_gap_m`] (SO-101 0.1101) together with the clearance; required, no default | The object's extent along the jaw line (TCP X). |
| `fixed_jaw_clearance_m` | m, >= 0, default 0 | Gap kept between the fixed fingertip face and the object at arrival. The closing jaw slides a free object this far toward the fixed jaw. |
| `grasp_depth_m` | m, [`min_grasp_depth_m`, `max_grasp_depth_m`] (SO-101 -0.0053..0.0611), default 0 | Distance of the centre behind the TCP origin plane, toward the palm: the finger section along the approach axis. |
| `quaternion_xyzw` or `fixed_jaw_yaw_deg` | unit quaternion, or deg in [-180, 180]; exactly one | Orientation of the TCP. `fixed_jaw_yaw_deg` is a straight-down approach with TCP +X (moving jaw to fixed jaw) at that yaw about `frame_id` +z from +x, i.e. `[cos(yaw/2), sin(yaw/2), 0, 0]`. |

The backend compiles the request parent-side, before validation: `position = grasp_centre_m + R(orientation) @ [object_width_m/2 + fixed_jaw_clearance_m - fixed_face_x, 0, grasp_depth_m]` (TCP axes; SO-101 `fixed_face_x` is 0). The jaw angle does not enter, because only one jaw moves: the fixed fingertip face is the reference and the moving jaw closes the rest. The compiled leaf keeps the request as `input_grasp_centre`, and the backend validator re-derives the target from it, so a leaf whose target and request disagree is refused. Everything else on the stage (`gripper_goal_normalized`, `gripper_motion`, tolerances, `approach_tolerance_rad` / `roll_tolerance_rad`, speed, stall guard, grip guard) applies to the converted target as on any move, `mode=reach` accepts the same fields, and a continuation override that switches between the two pose forms drops the fields of the other form.

Results name the conversion: preview `stage_plans[<stage>].grasp_centre` and reach `stage_results[<stage>].grasp_centre` carry the request, `tcp_target_position_m` / `tcp_target_quaternion_xyzw`, `tcp_offset_tcp_m`, `fixed_jaw_direction` and `approach_direction` (unit vectors), `jaw` (`straddle_gap_m`, `straddle_goal_normalized`, `closed_on_object_goal_normalized`, `closed_on_object_jaw_rad`, `moving_fingertip_depth_m`), `object_shift_on_closing_m` and `planned` (`grasp_centre_m`, `centre_error_m`: where the planned joints put the centre; an orientation residual the tolerances accept moves the centre about the TCP although the TCP position matches). Executed `stage_results[<stage>].grasp_centre` repeats the request and `tcp_target_position_m`. A move with an after-arrival jaw goal is split into `<id>/motion` and `<id>`; the report is on the motion stage.

Preview also returns `grasp_3d_review` for grasp-centre stages after which the jaw does not open (`grasp_preview_3d.audit_batch_jaw_grasp`). It compares reported numbers without margins: the jaw goal the move arrives with against `straddle_goal_normalized`, the closing goal against `closed_on_object_goal_normalized`, a resolved `min_aperture_m` against `object_width_m`, `planned.centre_error_m` against the stage's `position_tolerance_m`, and, when an object-table row contains the commanded centre, the centre height against the row's top and bottom, the fingertip height against the support, the row's box extent along the jaw line against the declared width (the fixed fingertip face inside the object) and against `max_gap_m`, and the jaw line against the long axis of an elongated row. Warnings are advisory; `execute_if_clean` returns the preview instead of executing when one exists (`grasp_3d_review_warnings`). Details and the CAD numbers: [SO-101 integration §4.9](so101-integration.md#49-grasp-centre-input-grasp_centre_m).

### Path facts, path check, collision world and arrival correction (SO-101 profile tags)

Four more opt-in tags ([embodiment-profile.md](embodiment-profile.md#supports-tags)); ARX X5 carries none of them and its schema is unchanged.

- Every SO-101 preview reports `stage_plans[<move>].path`: forward-kinematics facts of the joint-space line the move will follow (`min_tcp_z_m`, `min_fingertip_z_m`, `lowest_at_fraction`, `max_line_deviation_m`, `dip_below_endpoints_m`, m), and the trajectory overlay is sampled from that line. Execution reports `path_start_deviation_rad` per move.
- `path_check` (SO-101 with the cuRobo IK service) adds the preview review `path_check`: every move's joint path is sampled and checked against self-collision, the table box and the request's boxes; `status` is `clear`, `collisions` or `unavailable`, and a colliding move carries `stage_plans[<move>].path.collision` (first colliding sample: `fraction`, `tcp_position_m`, colliding links, penetration and obstacle ids). The jaw is checked at the angle it has at each sample: a move with `gripper_motion` is checked as up to three segments cut at its `start_fraction` / `end_fraction` (`ik_plan.path_check_segments`), so the checked jaw follows the streamed ramp. The review is advisory: the plan stays `planned` and executable. `execute_if_clean` runs only on `clear` and otherwise returns the plan with `downgrade_reasons` `path_check_collisions` or `path_check_unavailable`.
- `collision_world` (+ `obstacle_object_ids`) offers `obstacles`, `obstacle_object_ids` and `held_object` on a robot without the proxy review. The boxes use the proxy form (`id`, `min_m`, `max_m`, `evidence`, optional `margin_m`), apply to that request only (no registry, so no `obstacle_policy` / `ignore_obstacle_ids`), and enter the planner's collision world: IK targets prefer solutions clear of them (`ik.obstacle_free`) and the path check names them. The size rules that turn an `obstacle_object_ids` row into a box (minimum footprint, half extent and height, defaults for missing values; `scene_obstacles.ROW_*`) are published in that field's help, and the preview's `path_check.object_row_boxes` lists ids that added no box (`skipped` with `not_in_table`, `held_row`, `no_centre` or `no_object_table`) and every size rule that changed a box (`size_floors`); it is absent when there is nothing to report. `held_object` is carried with the gripper until the first stage that opens the jaw. `held_objects` and the contact declarations are not offered.
- `arrival_correction` adds `arrival_correction_rounds` (integer count, 0 = no goal shift after settling) and `arrival_correction_max_offset_rad` (rad per joint) on move stages and as batch defaults; the stage value wins, omission uses the robot's limit, a value above that limit is refused, and `effective_tolerances` reports the bounds used. The limit is the profile's `arrival_correction_limits` (SO-101: the deployment's `motion.arrival_correction_*`), published as the schema `maximum` and in the field help, so the schema refuses exactly what the backend would. A `mode=reach` result carries no arrival-correction bounds (nothing moves).

A failed SO-101 move also mirrors its measured TCP residual to receipt level as `endpoint_residual_m` (the ARX-X5 field) and sets `in_hand_tracking_error` when the closed jaw still holds something. Details and numbers: [SO-101 integration §4.9, §4.10, §12.8 to §12.11](so101-integration.md#410-arrival-correction-bounds-per-move).

`preview` is the default mode and does not advance the simulation. An executable plan is returned only if the entire batch compiles; if any later stage fails planning, no earlier stage is executed. `execute` dispatches the exact cached trajectory after verifying environment identity, measured starting state, remaining budgets, and first-step joint jumps—never silently replanning. Resuming from an observation checkpoint additionally verifies the execution cursor and checkpoint state. Replaying an identical request is idempotent and does not re-execute motion. Changing targets, routes, or invalidating the plan requires a fresh preview. Explicit `direct` mode plans and executes in a single call.

### Fast Planning Modes (`preflight`, `execute_if_clean`) and `image_delivery` / 4D Trajectory Receipts

To eliminate unnecessary multi-turn preview round trips and support configurable post-action image payloads while preserving safety and closed-loop observability, `robot_action` provides two additional planning/execution modes and an `image_delivery` contract:

- **`mode="preflight"`**: Runs the exact same physics-free kinematic/IK compilation, principal-branch joint-travel admission (`rad`), native step/time cost (`s`), per-stage `effective_tolerances` (`m`, `rad`), vectorized 3D grasp/collision checks (`grasp_3d_review`), and numerical `trajectory_summary`, and caches `plan_id` for `mode="execute"` while skipping trajectory overlay rendering (`0` images returned). Ideal for fast multi-candidate checks or loops inside `program_run`.
- **`mode="execute_if_clean"`** (or `auto_execute_if_clean=true` on `preview`/`preflight`): Compiles the batch and runs `motion_safety`, `grasp_3d_review`, and `geometry_review`, then immediately executes in the **same** call when hard `blocking_risks` (e.g., jaw opening narrower than object cross-section, physical neighbor collision, or motion safety failure) are empty. Soft `advisory_notes` (such as oblique grasp yaw suggestions or thin-object `contact_stop` support clearance notes) are reported transparently in the receipt without blocking execution. If hard `blocking_risks` are present, `execute_if_clean` does not move the robot and returns the cached `plan_id` with `0` overlay images (unless `image_delivery="all"`), allowing the model to inspect and either execute or revise the pose.
- **`image_delivery` (`"all"` default via `images.action_feedback_policy`, `"on_anomaly"`, `"none"`, `"focus_roi"`, `"head_only"`)**: When omitted on execution, `robot_action` resolves to `images.action_feedback_policy` (default `"all"`, delivering updated camera views alongside trajectory overlays when `features.action_trajectory_delivery="automatic"`). When configured or called with `"on_anomaly"` (and `features.action_trajectory_delivery="diagnostic"`), clean `completed` batches with valid 3D perception deliver `0` camera/trajectory images alongside `object_table` rows, `object_state_delta` (`m`, `deg`; workspace-wide persistent IDs when `features.persistent_object_tracking=true`), and a 4D `compact_3d_trajectory` (`process_trajectory` containing fingertip optical-flow `co_motion`, closed/pinching-jaw `slip_detected`, `in_place_motion` in `deg`/`m` for fastening or hinging, and `event_keyframes`), while automatically attaching diagnostic RGB and a single-panel `640×480` composite trajectory overlay whenever a stage stops/pauses, mid-transport slip is detected (`slip_detected=true`), or 3D perception is unavailable. Models can also pass `image_delivery="head_only"` or inspect 1:1 sensor crops via `robot_observe(focus_3d={...})`. See [`tests/runtime/actions/test_preflight_and_execute_if_clean.py`](../../tests/runtime/actions/test_preflight_and_execute_if_clean.py), [`tests/runtime/harness/test_prefix_cache_and_on_anomaly.py`](../../tests/runtime/harness/test_prefix_cache_and_on_anomaly.py), [`tests/runtime/actions/test_rollout_4d_ledger.py`](../../tests/runtime/actions/test_rollout_4d_ledger.py), and `tests/unit/test_vectorized_grasp.py` (retired).

In addition to explicit `observe` stages, `robot_action` (API version `1.1`) accepts an optional boolean `checkpoint_after_gripper` (default `false`) on `move`/`gripper` stages containing a gripper command or at the batch top level. When explicitly enabled—and when that gripper command window changes the gripper goal and is followed by a dependent `move` stage (via same-arm ordering or `depends_on`)—the compiler automatically inserts an observation checkpoint at the existing native cursor at the end of that window (setting `false` on the window's final stage overrides a batch-level `true`, and an existing explicit checkpoint at the same cursor is merged). Preview `checkpoints` and execution `checkpoint_stage_ids` report the triggering stage ID. Execution pauses with `stopped` / `observation_checkpoint`, a formal terminal observation, and a typed receipt, allowing the model to resume the same `plan_id` with zero replanning. When omitted, the batch executes continuously without interrupting routine gripper openings or post-release withdrawals.

The grip-guard and `checkpoint_after_gripper` decisions are shared functions in `ni_rua/robot/motion/grip_guard.py` (`stage_grip_guard`, `after_stage_grip_guard`, `jaw_checkpoints`), used by the ARX-X5 batch executor and the SO-101 worker. Presets are margins above the gripper's empty-close gap (`profile.gripper.empty_close_aperture_m`, 0 m on ARX-X5) and explicit `min_aperture_m` / `max_aperture_m` are absolute gaps in `[0, profile.gripper.full_open_aperture_m]` (X5 0.088 m, SO-101 its measured full opening); the validators, the schema bounds and the help text all read those profile values. SO-101 numbers and limits: [SO-101 integration §4.1](so101-integration.md#41-grip-guard-and-checkpoint_after_gripper).

Because a checkpoint pauses both arms, an independent stage running on the opposite arm also pauses at the shared cursor and resumes along its cached trajectory afterward; within a single stage, any motion remaining after an in-motion synchronized gripper ramp finishes to the end of that stage before pausing. Terminal gripper stages, commands that do not change the latched goal, and gripper stages without downstream physical dependents do not add checkpoints; stages already separated by an explicit `observe` continue to follow explicit observation boundaries.

For parallel-jaw open-jaw approaches and pre-grasps on ARX X5 (where rotating the tool flange by $180^\circ$ about its local approach axis $+X_{\mathrm{local}}$ preserves exact 3D jaw-plane geometry and `grasp_position_m`), `robot_action` accepts an optional boolean `allow_jaw_symmetry` on `move` stages or at the batch top level (defaulting to `true` on `grasp_position_m` `move` stages; pass `allow_jaw_symmetry=false` when camera/cable side or asymmetric fixture clearance requires a single fixed jaw side). When enabled and the arm's starting normalized gripper opening is at least `0.90`, if the requested orientation fails IK or joint-travel limits, planning evaluates strictly the exact $180^\circ$ $SO(3)$ parallel-jaw twin (`R_local(x, 180 deg)`). Contact-center-invariant $\pm 15^\circ / \pm 30^\circ$ approach tilts are never tried automatically—pass explicit opt-in `allow_approach_tilt=true` (default `false`) on a `move` stage or batch when mild approach tilt is physically acceptable; when an open-jaw `grasp_position_m` move fails `path_infeasible` with `allow_approach_tilt=false` and one or more $\pm 15^\circ / \pm 30^\circ$ closing-axis tilts are feasible, the failure summary and `failure_feedback` report `feasible_approach_tilt_angles_deg` (`deg`, keeping `grasp_position_m` fixed) and a factual `failure_hint` without mutating or executing the stage. Both preview `stage_costs` and execution `stage_results` transparently report `jaw_symmetry_resolved=true` (and `approach_tilt_resolved=true` when opted in) alongside `resolved_angles_deg` (`deg`); closed-jaw or holding `move` stages strictly preserve the caller's requested rigid orientation without silent rotation or tilt (see [`tests/robot/motion/test_batch_motion.py`](../../tests/robot/motion/test_batch_motion.py)).

Batch execution currently runs under the `resampled` native mode, supporting up to 32 stages total (up to 16 per arm; `profile.max_stages` / `stages_per_arm`) and, on RoboDojo, at most 250 native steps across the entire batch (`profile.per_request_step_limit`, 10 s at 25 Hz; including segments resumed across observation checkpoints). A robot with a real-time clock has no native step budget (SO-101: limit `null`, bounded by the request deadline instead; the default deadline is `profile.default_action_timeout_s`, from the deployment file on SO-101, 120 s on X5). The plan cache holds up to 16 plans; evicted plans or plans predating a native worker rebuild cannot be executed. Executed trajectory evidence remains inspectable via `mode="inspect", action_id=...` or a saved `trajectory_ref` (paginated by default, or complete via `detail="full"`).

Joints, end-effector poses, and gripper values in a preview represent planned commands, whereas execution returns actual measurements, failure or partial-execution statuses, and synchronized frame images. Obstacle and held-object bounding boxes are caller estimates, and held-object clearance assumes rigid attachment. Unavailable geometry is reported as `unknown` rather than certifying collision-free motion. Contact declarations only annotate geometric clearance estimates and never prove physical contact, grasp retention, or object support.

Default action feedback preserves per-joint first-step jump magnitudes and allowed limits (`first_joint_step_rad`, `max_joint_step_rad`) as well as segment-start tracking deviations (`max_joint_start_error_rad`) on failure. Trusted action summaries in the program broker likewise retain these diagnostics alongside per-stage endpoint errors, contact-reference position feedback, full stage diagnostics, and unknown extension fields; program summaries cover all actions executed by the job so early failures are never evicted by a sliding window.

For failed previews, self-collision model diagnostics pass through the information boundary check and deliver all sampled witnesses in full rather than truncating to the deepest three. The existing `planner_collision_witnesses` JSON artifact and `collision_model_witnesses_ref` remain available for inspection. Joint position, velocity, acceleration, and jerk constraint checks likewise retain the worst violation per joint so none are dropped outside a top-three cutoff. These witnesses derive solely from candidate trajectories and the public robot model—not from executed collisions or ground-truth environment contact. If artifact archiving fails, the boundary-validated witnesses are still delivered inline alongside an archive error diagnostic; any data failing permission or serialization checks is withheld. This behavior does not backfill dropped witnesses in historical archives or recover uncaptured solver seeds and intermediate optimizer paths.

Failed previews are also recorded as `action.batch_preview` events, preserving the public failure reason, safety witnesses, source observation binding, and budget snapshot. The recovery ledger links actor tool requests and public `program.call_started` broker requests to their corresponding previews within the same episode, thread, turn, and call identity (previews inside programs undergo the same evidence validation and are never fabricated from `stdout` or evaluator state). Entries are recorded only when zero physical steps occurred and the observation/budget bindings match; a candidate is marked as a budget rejection only when its known cost exceeds the remaining budget with a matching budget-rejection witness. Unknown costs or IK failures are never misclassified as insufficient budget. Duplicate results for the exact same candidate are deduplicated while changes in status, cost, or evidence are retained. No single candidate rejection proves the overall task is infeasible. See `test_unified_actions` and `test_recovery_evidence` for regressions.

## Program Review and Active-Work Timing

By default, `program_run(operation="start", source=...)` does not grant direct physical action authority. When a program calls `client.action(...)` or `client.call("robot_action", ...)` to execute motion, the broker first compiles a preview, freezes the program's process group, and returns `awaiting_review`, a `review_id`, the preview data, and overlay images to the primary model:

```json
{"operation": "resume", "job_id": "<returned job_id>", "review_id": "<returned review_id>", "decision": "approve"}
```

Approving executes the reviewed cached plan; rejecting returns a rejection payload to the Python program so it can handle the decision. If another call invalidates the cached plan while review is pending, the stale review cannot proceed. A program cannot call `resume` to approve itself or use legacy tool names to bypass review. Because `robot_wait` advances physical time, it also requires review.

The primary model may pass `allow_direct_actions=true` at `start` time to authorize direct execution for that specific program run; permissions, source code, and action arguments cannot be modified during `resume`. Review logic is centralized in the broker and currently approved autonomously by the primary model without waiting for a human operator.

Program active-work timeout defaults to 180 seconds (maximum 300 seconds) with no cap on tool call count. Active-work timing excludes wall-clock time spent waiting for auxiliary models or primary-model review. Cancellation remains available while paused for review and cleanly thaws and reaps the process group. Once the program process has exited, the rest of its process group (descendants it left behind) is killed; the stop counts only when the group is gone within 2 s (`STOP_CONFIRM_S`; macOS answers EPERM while an exited descendant waits to be reaped, which is not taken as an answer either way), otherwise the job is `unknown` with `stop_confirmed=false` and `reason="program_descendant_stop_unconfirmed"`, its `returncode` kept. A program that exits just as its review pause starts fails the reviewed call with `program_exited_before_review` on every host. Process exit codes and `action_summary` are tracked separately: action outcomes are collected exclusively from trusted broker replies, never inferred from `stdout` or exit code `0`. Terminal frame images are delivered via native dynamic image items.

A `direct` action can also fail during the planning phase. Only when the typed `plan` result explicitly records `status=failed`, `physics_advanced=false`, and an integer step count of `0` does the program's `action_summary` record `not_executed` / `phase=planning` while preserving the failure reason and prior observation (without generating an action receipt). If those proofs are absent or the execution channel is interrupted, the outcome remains `unknown` with an unknown step count—never backfilled as zero based on display text or outer `success`.

## Optional Settling Wait and Operational Memory

Actions return immediately upon completion by default. Passing an explicit `settle={"roi": [x, y, w, h], "max_native_steps": 25}` runs bounded visible-motion settling detection (capped at 50 native steps) using standard `robot_wait` calls that count against the native action budget. Consecutive trackable low-displacement frames only indicate low visible motion within the ROI; camera motion or insufficient texture returns `unknown`. Settling results are reported separately from the primary action receipt, and the current observation ID advances to the final post-wait frame. Standalone `robot_wait` remains available.

`operation_memory` stores and retrieves operational experience across any manipulation phase. Queries for `scope="task"` and `scope="shared"` are kept strictly separate, and cross-task memories must state their applicability conditions. Recording a memory verifies action and observation ownership and extracts execution facts directly from run history. Historical coordinates and past task-success judgments never substitute for live observations.

## Compatibility Boundaries

Legacy motion tools, standalone preview/cost tools, queues, manipulation templates, fixed skills, grasp tables, and `scene_*` tools are no longer exposed to models in new runs. Optional visual manipulation review is consolidated into `vision_review(evidence_mode="operation")`. Legacy native execution and history-parsing adapters remain in the codebase for reading historical archives and testing low-level mechanisms, without granting model or program execution entry points. Legacy program-template tests run through test-only adapters; no production flag re-enables them.

The presentation layer strips versions, hashes, source file paths, and duplicated request payloads, retaining only actionable/inspectable short IDs and essential measurements while preserving full raw evidence and trajectories in the archive. Image selection policies, high-frequency feedback decisions, and auxiliary-model review policies are never altered by presentation formatting.

## Registration and Internal Boundaries

The `ToolSpec` declaration for `robot_action` drives the model catalog, actor calls, and program calls alike. Running under the `feedback` backend mode, `unified_action.available=false`, or an uncalibrated observation profile marks `robot_action` unavailable and rejects direct calls before entering the handler. The legacy `motion_review` toggle governs historical single-arm previews and does not disable the unified `resampled` batch interface. Default effects are `plan` for `preview`/`preflight`, `physical` for `execute`/`direct`/`execute_if_clean`, and `read` for `inspect`.

Batch compilation calls the backend's `compile_action(kind, arguments, identity, capabilities)` hook (`arx_actions.compile_action` for the RoboDojo X5 backend) directly rather than routing through legacy tool names or private `Harness` conversion methods. `Harness` retains ownership of identity, current observation tracking, action admission, single-writer physical dispatch, and immutable receipts, while the backend enforces native constraints through its `validate_action` port. New actions cannot be planned when the current observation is unavailable, whereas replaying an already committed `action_id` returns its original persisted record.

Review and execution return internal `ToolResponse(kind="plan"|"action", data=...)` objects consumed directly by both the program broker and generated programs; client-facing `kind/data` copies undergo the same provenance filtering and short-reference resolution while retaining `contentItems` for wire compatibility. Primary-model native tool replies continue to use `{success, contentItems}`. For adding new tools, see [Tool Registration and Extensions](tool-plugins.md).

`grasp_position_m` specifies the center point between the two fingers on the selected contact cross-section—not the surface of a single finger—and `contact_region` selects the axial cross-section along the finger without guaranteeing physical object contact. `position_tolerance_m` checks the measured TCP position (`link6` on ARX X5, `gripper_frame_link` on SO-101) and `orientation_tolerance_rad` checks measured orientation; when a stage names neither a preset nor an explicit tolerance, `profile.default_tolerance` applies (ARX X5: `10 mm` and `0.15 rad` with `max_upward_dz_m=0 mm` and `max_downward_dz_m=0 mm` under `tolerance_preset="normal"`; SO-101: the deployment's `motion.default_position_tolerance_m` / `default_orientation_tolerance_rad`, with `max_upward_dz_m=0 mm` arrival rule; explicit `max_upward_dz_m`, `max_downward_dz_m` on ARX X5, `tolerance_preset="compliant"`, or `stall_guard_preset="contact_stop"` configures vertical compliance per stage). Tracking failure halts subsequent stages, including not-yet-dispatched gripper commands; relaxing tolerances never implies physical contact occurred. Completing a gripper command or measuring a change in jaw aperture likewise does not prove an object is held; verify retention using task-appropriate observable evidence.

## Explicit Motion and Held-Evidence Contract

Grasp-angle planning preserves the requested orientation. Infeasible poses return a planning failure so the actor can explicitly choose new angles and preview again; joint-space replanning remains available without altering the Cartesian target. Vertical compliance never relaxes the declared orientation tolerance, and downward error remains bounded by the declared position tolerance. Contact-stop modifies only stopping behavior and the documented upward compliance window, never declared horizontal or angular tolerances.

Held-object metadata reports `retention_status="unverified"` (no retention assertion), `attachment_assumption="rigid_since_grasp"` (conditional kinematic model), `geometry_evidence="current_mask"|"prediction_only"` (availability of usable current segmentation), and `current_mask_views` (head/wrist views with usable masks). These categorical fields carry no physical units and appear on both carried and fallback rows; a current mask does not establish co-motion. Prediction-only rows remain available during occlusion but cannot establish a successful grasp or continued retention. No additional observation or model call is incurred.
