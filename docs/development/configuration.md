# Unified Configuration and Feature Flags

`ni_rua.core.config.Config` is the unified configuration entry point for new runs. The default configuration file in the repository is `configs/ni-rua.json`, and a complete annotated example is available in [`configs/ni-rua.example.json`](../../configs/ni-rua.example.json). In practice, you only need to specify the fields you want to override; all omitted fields inherit defaults from the `Config` class. Because JSON does not support comments, this document serves as the reference for every configuration field, dependency, and legacy environment variable mapping.

When building a wheel, `scripts/build_package.py` copies the repository default file into the package as `ni_rua/default_config.json`. Installed wheels fall back to this packaged copy when running outside a repository checkout, so new experiments share identical defaults whether run from source or from a wheel. Explicit `--config` / `NI_RUA_CONFIG` overrides still take precedence, and `Config.from_dict()` preserves historical defaults when loading older archives.

## Usage and Override Precedence

All project commands below run inside the Miniforge `ni-rua` environment; for environment creation and verifying the resolved Python interpreter and Codex SDK/CLI versions, see the [Running Guide](running.md#environment-setup).

```sh
# Run with the repository default configuration
mamba run -n ni-rua python -m ni_rua.apps.gateway --run-dir runs/my-run --gpu 4

# Use a custom experiment configuration; CLI flags override settings for this run only
mamba run -n ni-rua python -m ni_rua.apps.gateway --config configs/my-experiment.json \
  --run-dir runs/my-run --gpu 4 --no-enable-wait

# Validate and print the full effective configuration without starting models, GPUs, or services
mamba run -n ni-rua python -m ni_rua.apps.gateway --config configs/my-experiment.json --print-config

# Point all unified-config entry points to a specific configuration file
export NI_RUA_CONFIG=/absolute/path/ni-rua.json
```

Configuration layers merge in the following order:
1. `Config` class defaults
2. Compatible legacy environment variables
3. Repository default file `configs/ni-rua.json` (or the packaged fallback in installed wheels)
4. Local repository override file `configs/ni-rua.local.json` (if present)
5. Explicit JSON configuration file (`--config` or `NI_RUA_CONFIG`)
6. Explicit CLI flags

Nested objects merge field-by-field, so an experiment configuration that only overrides `features` still inherits the default model and local Codex home, while an explicit configuration specifying legacy model settings can still override the newer defaults. `--config` takes precedence over `NI_RUA_CONFIG`; when both are omitted, the merged public and local defaults are used. Every configuration file is strictly validated on load, and relative paths inside a file resolve relative to that file's directory. Unpassed CLI flags never overwrite file values. Unknown field names, invalid types, non-finite numbers, and unsupported enum values are rejected before any service, model, or robot worker starts.

Relative paths in JSON files resolve relative to the directory containing that file, whereas CLI and legacy environment variable paths resolve relative to the current working directory (`~` is expanded in both cases). Saved effective snapshots store resolved absolute paths. The minimal valid JSON file is `{"version": 1}`, as the `Config` class supplies all defaults. Because `configs/ni-rua.example.json` uses `~` paths, review its `backend` and `policy` sections when copying it to another machine.

Array fields replace the previous list as a whole—for example, passing `--tag trial` replaces the tags defined in the config file, and `--clear-tags` empties the list. `null` in JSON is only valid for optional fields that explicitly permit `null` in the schema; never use `null` to disable a boolean flag (use `false` instead).

For example, the file below keeps the default calibrated observation profile, disables `robot_wait` and $\pi_{0.5}$, and enables tracking protection and compact actor payloads:

```json
{
  "version": 1,
  "features": {
    "enable_wait": false,
    "pi05": false,
    "tracking_guard": true,
    "actor_payload_profile": "compact_v1"
  },
  "images": {
    "reuse_exact_images": false
  }
}
```

New runs enable `robot_wait` by default. Disabling it only removes the model's ability to call `robot_wait`; it does not change whether observations advance physical simulation time (`robot_observe`, model thinking time, and wall-clock sleeps never advance the paused simulation).

Python callers share the same immutable `Config` object so individual modules never re-read environment variables or diverge in defaults:

```python
from ni_rua.core.config import Config

config = Config.load("configs/my-experiment.json").validate_launch()
assert config.features.enable_wait is False

# Returns a new Config instance without mutating the original; an explicit False is never treated as "omitted".
candidate = config.with_overrides({"features": {"enable_wait": True}})
snapshot = candidate.to_dict()

# Loading from an archived dictionary does not read current environment variables or default files.
restored = Config.from_dict(snapshot)
```

`Workbench`, `Harness`, `RobotBackend`, `CodexSession`, and the Experiment Library all accept `config=`, while preserving existing explicit constructor keyword arguments for backward compatibility. Loading a configuration and running `validate_launch()` do not start any external services.

| `model.codex_home` | `~/.codex` (repo default for new runs) | Host directory from which local Codex provider routing and credentials are read; host extensions are not inherited, sessions run in a per-run private directory, and OS isolation is governed by `features.sandbox_enabled`. |

| `model.transport_recovery.max_rounds` | `10` | Maximum cooldown-and-resend rounds (1 HTTP attempt per round) after the 12 automatic retries for explicitly retryable errors are exhausted or after an upstream `transport_incomplete` disconnect; `0` disables recovery, maximum `20`. |
| `model.transport_recovery.initial_delay_s` / `backoff_multiplier` / `max_delay_s` | `60` / `2` / `600` | Cooldown schedule across rounds: `60`, `120`, `240`, `480`, `600`... seconds. |

Configuration files never store API tokens or duplicate provider secrets. Provider endpoints, authentication methods, and upstream URLs remain managed by the native Codex configuration and credential files inside `model.codex_home`, and provider API keys in environment variables continue to be resolved as usual.

On a local workstation, you can use a Git-ignored `configs/ni-rua.local.json` to point to a dedicated provider home—for example, `{"version": 1, "model": {"codex_home": "~/.config/ni-rua/providers/my-provider"}}`. Keep only the directory path in `configs/ni-rua.local.json`, and place the provider's `config.toml` and key-bearing `auth.json` inside that external directory with directory permissions `0700` and file permissions `0600` (including `configs/ni-rua.local.json`). Never place raw API keys inside unified JSON configuration files, because resolved configurations are written into manifests, experiment archives, and web reports. Using a dedicated Codex home prevents provider changes from affecting interactive Codex CLI sessions or already running queues, and `configs/ni-rua.local.json` is never bundled into wheels. An explicit `--config` still overrides `configs/ni-rua.local.json`, and neither `Config.from_dict()` nor already frozen queues read the local override file, ensuring historical snapshots are never reinterpreted when local defaults change.

Both `configs/ni-rua.json` and `configs/ni-rua.example.json` explicitly select `gpt-6.1-sol`, `high`, and `~/.codex` for new runs, while local defaults or explicit configs can point to another isolated home. At startup, NI-RUA reads the active provider from `config.toml` in the selected home and reads credentials from `auth.json` or the provider's declared authentication settings, keeping real credentials strictly inside the host relay. The actor's private per-run home receives placeholder credentials without copying real API keys, `.credentials.json`, or host extensions from the source directory, and never writes back to the source directory. Never commit secrets to tracked config files, manifests, CLI arguments, or logs, and never check a source Codex home into Git. `model.price_card` defaults to `null` so pricing rules from another provider or model are not applied inadvertently.

The primary actor's model name and reasoning effort are governed strictly by the unified configuration and are not overridden by eponymous preferences inside the source Codex home. `Harness` pins `web_search = "disabled"`, `service_tier = "default"`, and the `Responses` wire protocol; the native provider identifier `ni_rua_model_proxy` points to the local accounting proxy, which forwards requests to the external upstream defined by the selected local Codex provider. When enabled, the optional auxiliary visual review model reuses the provider, proxy, and authentication prepared for the primary session, running `gpt-6.1-sol` / `high` in its own isolated home and thread without re-reading the source Codex home.

Default model selection for new runs lives solely in the repository configuration file; `Config.from_dict()` does not consult `configs/ni-rua.json`, so the static `Config()` defaults (`gpt-6.1-sol` / `high` / `~/.codex`) match `configs/ni-rua.json` exactly; archives always record the model explicitly in `effective_config.json`, which is what replay and comparison must read. Evaluation queues with a frozen `ni_rua_config` continue using their frozen snapshot. When launching a new experiment from an older manifest template, pass `--config configs/ni-rua.json` explicitly or regenerate the manifest. Note that a queue freezes the `codex_home` path rather than inlining secret files, so each case reads the provider files at that path when it launches; if you switch providers for future runs, create a new provider home directory rather than mutating a directory referenced by an active queue. The legacy `~/.config/ni-rua/experiments.json` file supports only `codex_home` and `price_card` paths; omit `price_card` entirely (rather than setting it to JSON `null`) when no price card is used.

`manifest.ni_rua_config` stores the resolved effective configuration snapshot; even if a historical snapshot has only a subset of fields, missing fields are interpreted using historical defaults. Supply partial configuration overrides for new runs via `--config`, which loads the current defaults first and freezes the complete resolved snapshot.

## Code Execution Sandbox

`features.sandbox_enabled` is a global boolean toggle defaulting to `false` in both the `Config` class and `configs/ni-rua.json`; set it explicitly to `true` to enable OS-level isolation. It simultaneously controls the Linux bubblewrap namespace around the primary agent session of every backend (Codex with its native terminal, subagents, shell commands and memory consolidation; Claude Code and OpenCode with their native tools and subagents), the bubblewrap namespace around the auxiliary Codex evidence agent, and Landlock/seccomp isolation for `program_run`. Its purpose for benchmarks is that the model cannot read the RoboDojo / simulator source (reward hacking); the published Harness source stays readable at `/harness`. RoboDojo comparisons across backends therefore run with the sandbox on for every arm; see [Agent Backends](agent-backends.md#sandbox-featuressandbox_enabled-all-backends) for the per-backend mounts. When set to `false`, NI-RUA neither probes nor loads these isolation mechanisms, so `bwrap`, `libseccomp`, unprivileged user namespaces, and Landlock are not required on the host (standard runtime dependencies still apply).

For example, save the following as `configs/no-sandbox.json` to disable the sandbox for a local diagnostic run:

```json
{
  "version": 1,
  "features": {
    "sandbox_enabled": false
  }
}
```

```sh
mamba run -n ni-rua python -m ni_rua.apps.gateway --config configs/no-sandbox.json --print-config
mamba run -n ni-rua python -m ni_rua.apps.gateway --config configs/no-sandbox.json \
  --run-dir runs/no-sandbox-trial --gpu 4
```

When disabled (`false`), each run still uses an isolated per-run `HOME` / `CODEX_HOME`, the local model relay, and placeholder credentials without inheriting host MCP servers, plugins, or skills, and `program_run` retains its FD broker, tool permission checks, action review, budgets, and resource limits (`RLIMIT`). However, executed code runs with the launching user's host filesystem and network privileges—private directories and placeholder tokens do not form an OS security boundary, and formal observation restrictions are enforced solely at the application layer. Consequently, unsandboxed runs do not provide OS-level proof that host files, credentials, evaluators, or observer artifacts were inaccessible; always record whether a run executed with or without the sandbox.

When the sandbox is disabled, the read-only copy of public Harness source code is staged at `<run>/private/actor-source` instead of being bind-mounted at `/harness`. The `sandbox_enabled` setting is persisted in the effective configuration snapshot; editing a config file on disk never hot-switches a running experiment or a frozen queue. Resuming a session across different sandbox modes is rejected (start a new run instead), and legacy full-access sessions lacking isolation markers cannot be migrated in place.

The isolation, mount, and controlled network rules below apply when `features.sandbox_enabled=true` is explicitly enabled. During `CodexSession._prepare()`, `Harness` launches the entire native Codex app-server inside a Linux bubblewrap sandbox. Isolated mount, PID, IPC, and network namespaces cover the primary thread, subagents, shell tool, and memory consolidation, running under the current user's UID/GID with all Linux capabilities cleared. `bwrap`, `sudo`, and `setpriv` are discovered from the current `PATH` and platform default `PATH`. NI-RUA prefers unprivileged user namespaces; only when the host kernel disables unprivileged user namespaces does it fall back to `sudo -n` to create the namespace and immediately drop privileges via `setpriv`. If sandbox initialization fails, startup aborts rather than falling back to unsandboxed host execution. The launch gate (`factory.backend_requirements`) accepts the sandbox for `codex`, `claude_code` and `opencode` alike; a host without bubblewrap is refused when the session starts, before the native agent process exists (`codex_sandbox_bubblewrap_not_found_on_path_or_os_defpath` for Codex, `agent_sandbox_bubblewrap_not_found_on_path_or_os_defpath` for Claude Code and OpenCode). On a host where the gateway user has supplementary groups, the unprivileged path cannot drop them inside the user namespace, so the rootful `sudo -n` fallback is used there as well.

The run directory, source snapshot path, and native Codex binary are resolved from the run configuration, the installed `ni_rua` package, and the pinned `openai-codex-cli-bin` package respectively, without hardcoding usernames, checkout paths, or Conda installation directories. IPC sockets use `XDG_RUNTIME_DIR` (or Python's platform temporary directory when unset); the runtime directory must be owned by the current user with `0700` permissions and have a short enough path to fit Unix domain socket limits (107 bytes on Linux, 103 on macOS). Without `XDG_RUNTIME_DIR`, when the platform temporary directory is too deep for the longest socket the session binds (for example the macOS per-user directory with an 8-digit or longer uid), Codex uses `/tmp/ni-rua-ipc-<uid>` instead, with the same ownership and `0700` checks; an explicit `XDG_RUNTIME_DIR` that is too long is refused (`codex_ipc_path_too_long`). System `python3` is discovered from the platform default `PATH`, its standard library path is queried from that interpreter, and required ELF shared libraries are resolved via `ldd`—NI-RUA never bind-mounts all of `/usr`, the Conda environment, or host `site-packages` / `dist-packages`. Paths such as `/harness`, `/tmp`, and `/usr/bin` refer to mount points inside the sandbox rather than host machine configuration paths.

System utilities are exposed inside the sandbox according to the explicit allowlist in [`system_runtime.py`](../../ni_rua/cortex/session/system_runtime.py), covering standard shell utilities, file operations, text search and comparison (`grep`, `diff`, `cmp` and the like), text processing, checksums, archiving, and local Git; `python` names the published system `python3`, and the C.UTF-8 locale files are published, so that a shell command run with `LC_ALL=C.UTF-8` (how the native agents run them) prints no locale warning and text tools are multibyte-aware. For Codex, `rg` is the one the pinned Codex distribution ships; the other agent backends take `rg` from the active environment. Optional utilities that are not installed on the host are simply omitted, and network clients, privilege and session tools, other interpreters and system package managers are never added to the list (`EXCLUDED_COMMANDS`; Python packages install through `python3 -m pip` and the private proxy). The same userland is published to the Codex, Claude Code and OpenCode sandboxes. Inside the sandbox, Python can install scientific computing packages through the private PyPI proxy, whereas other host binaries, compiler toolchains, and system package managers in `/usr` are not exposed.

Inside the outer bubblewrap container, Codex runs with `approval_policy="never"` and `sandbox_mode="danger-full-access"` so native tools can operate freely **within the outer OS sandbox**. OS isolation never relies on the model voluntarily following prompt instructions. The generated native configuration sets:

```toml
web_search = "disabled"
approval_policy = "never"
sandbox_mode = "danger-full-access"
model_verbosity = "high"
service_tier = "default"
project_root_markers = []   # no AGENTS.md from a git repository above the run (information boundary)

[features]
shell_tool = true
unified_exec = true
memories = true
multi_agent = true
multi_agent_v2 = true
hooks = true
goals = true
browser_use = false
browser_use_external = false
computer_use = false
apps = false
plugins = false
artifact = false
image_generation = false
network_proxy = false
code_mode_host = false
fast_mode = false
```

Inside the sandbox, `HOME` and `CODEX_HOME` point to the run's actor workspace and private session directory, system runtime dependencies are mounted read-only, and `/tmp` is private to the sandbox. `/harness` exposes a read-only snapshot of the public Harness, `ToolSpec`, action, and program interfaces as defined by the allowlist in `ni_rua/cortex/session/actor_source.py`. It excludes RoboDojo, backend task implementations, evaluators, reference policies, `.git` metadata, historical patches, experiment databases, the host home directory, and sibling repositories. `/harness` is provided for inspecting interface contracts; the full checkout is never mounted to satisfy arbitrary imports.

The isolated network namespace has no direct access to the host network or the public Internet. Traffic is forwarded exclusively over per-run Unix domain sockets to the local accounting model relay, the read-only account relay, and the controlled Python package proxy. The package proxy permits HTTPS requests strictly to `pypi.org` and `files.pythonhosted.org` so `python3 -m pip install <package>` installs into the actor's private workspace and cache; arbitrary websites, host loopback services, SSH, Git remotes, and alternate package mirrors are unreachable. Web search, browser tools, and external app/MCP integrations are disabled, and the model relay rejects server-side web search or remote tool invocations.

Host provider routing and credentials are read by `Harness` and remain inside the host relay; the sandboxed Codex process receives only the local relay URL and placeholder credentials. Supported host authentication methods include API keys or ChatGPT access tokens in `auth.json`, provider `env_key` variables, and bearer tokens, with custom auth headers restricted to `Authorization` and `ChatGPT-Account-Id`. Real `auth.json` files, `.credentials.json`, MCP servers, plugins, skills, and host conversation history/memories are never copied into the run, and the source Codex home (or CC Switch configuration) is never modified. Note that ChatGPT access tokens are read once when the host gateway starts—the sandbox cannot refresh host login sessions if a token expires mid-run.

Dynamic robot tools continue to use the direct tool catalog with `code_mode=false` and `code_mode_host=false` so image outputs are delivered as structured image items in `Responses`. The model name and reasoning effort come from the unified configuration, while native background requests (such as memory consolidation or thread titling) are accounted separately under their actual role and model. `model.native_memories=true` enables per-run native file memories (set to `false` to disable), which remain completely separate from NI-RUA's `operation_memory` and `grasp-memory`.

The standalone auxiliary evidence agent runs in its own separate bubblewrap namespace with an empty workspace and dedicated IPC socket—mounting neither the primary actor's workspace, `/harness`, nor the PyPI proxy—and receives only the selected evidence payload with all tools disabled. `program_run` retains its dedicated FD broker and Landlock/seccomp filter, restricting Python imports to the standard library and approved scientific computing packages while disabling host `.pth` files and unapproved Conda/`site-packages` directories. All physical robot actions from programs still pass through the single `Harness.execute` admission point.

## Feature Flags

| Field | Default (New Runs) | Controlled Behavior |
| --- | --- | --- |
| `features.sandbox_enabled` | `false` | Global toggle for the bubblewrap namespace of the primary agent (every backend), the auxiliary Codex evidence agent, and `program_run` Landlock/seccomp isolation (enabled only when explicitly set to `true`). When `false`, code runs with the launching user's host file/network permissions while retaining application-level tool validation, action review, and budgets; see [Code Execution Sandbox](#code-execution-sandbox). |
| `features.observation_profile` | `rgb_proprio_calibrated_v1` | Permits RGB images, proprioceptive state, exact camera/robot calibration, and the public robot model. Also supports legacy `rgb_proprio_v1`, while explicit `rgbd_proprio_calibrated_v1` is required to enable native depth capture and numeric depth tools. |
| `features.motion_review` | `true` | Enables advisory motion preview, cached plan execution, and optional grasp planning/memory tools; numerical risk diagnostics do not block execution. Automatically disabled under the uncalibrated legacy observation profile. |
| `features.default_task_notes` | `true` | Injects versioned operational experience notes into new benchmark runs; custom `run.task_notes` can still be used when disabled, and non-benchmark smoke runs do not inject default notes. |
| `features.self_briefing` | `false` | Optional pre-action model call that writes short operating notes before the initial turn (`ni_rua/cortex/context/self_briefing.py`); disabled by default (`--[no-]self-briefing`) to save ~35 s of pre-first-action turn latency. |
| `features.startup_inline_grounding` | `true` | Embeds initial `obs_1` measured robot state, `cam_head` overview RGB, and `obs3d` (`object_table` + `scene3d` handle) directly into the opening turn (`--[no-]startup-inline-grounding`), eliminating a separate startup `robot_observe` call. |
| `features.startup_grounding_views` | `overview` | Selects camera views embedded when `startup_inline_grounding=true` (`'overview'` embeds `cam_head` only; `'all_cameras'` embeds `cam_head` plus wrist views). |
| `features.action_trajectory_delivery` | `automatic` | Post-action trajectory overlay policy (`'automatic'` or `'diagnostic'`): `'automatic'` (the default) attaches trajectory overlays to executed actions; `'diagnostic'` returns compact 3D numerical trajectory summaries with `0` trajectory images on normal `completed` batches and attaches a single-panel `640×480` composite trajectory overlay on stops/anomalies. |
| `features.budgeted_action_reply` | `true` | Lays every actor action reply out by decision value (execution result, scene change, post-action observation, per-stage detail, trajectory feedback) on every agent backend. Where the agent host has a known text limit for one tool result (Codex 48,000 UTF-8 bytes from the pinned model catalogue, Claude Code 500,000; none known for OpenCode and external hosts) and the reply exceeds it, blocks are replaced, least valuable first, by a reference naming the existing call that returns them. `false`: no layout, no replacement. See [Actor Reply Delivery](tool-output-contract.md#actor-reply-delivery) (`--[no-]budgeted-action-reply`; queue case option). |
| `features.vision_compare` | `true` | Enables RGB feature comparison (`vision_compare`) and RGB skills that depend on it; disabling it does not affect explicitly enabled RGB-D skills. |
| `features.robotic_view` | `false` | [Wrist View Solver](robotic-view.md): computes `link6` poses from a caller-specified camera viewpoint; requires calibrated observations and returns preview parameters without moving the robot. |
| `features.stereo_guide` | `false` | [Stereo Epipolar Guide](stereo-guide.md): renders the epipolar line of a source pixel onto another synchronized camera view; requires calibrated zero-distortion pinhole cameras and does not perform automatic feature matching or triangulation. |
| `features.depth_auto_feedback` | `false` | Automatic pre/post-action numeric depth verification for registered targets; requires an RGB-D profile and adds no extra captures or physical actions. |
| `features.depth_skills` | `false` | Bounded grasp-and-lift and place-release-retract depth skills (requires RGB-D profile). Because the `skill_run` execution tool was removed in the 2026-10 refactoring, this flag currently only affects the `enabled` field in the `depth_query` `skill_help` catalog. |
| `features.depth_event_payload` | `false` | Allows routine intermediate actions with reliable depth measurements to deliver numeric summaries in place of inline images while still archiving full images; requires both an RGB-D profile and `depth_auto_feedback`. |
| `features.enable_wait` | `true` | Exposes `robot_wait` to explicitly advance simulation by 1–50 native steps and return temporal image frames. |
| `features.pi05` | `false` | Exposes the $\pi_{0.5}$ short-horizon policy prefix tool matched to the ARX X5. |
| `features.visual_review_model` | `null` | Disables auxiliary visual/operation verification by default; set explicitly to `gpt-6.1-sol` to enable `vision_review`, which shares the episode's model request budget. |
| `features.tracking_guard` | `false` | Halts end-effector motion when sustained joint tracking error exceeds thresholds, returning partial execution evidence. |
| `features.joint_replan` | `true` | Searches for closer valid $2\pi$-equivalent joint targets and substitutes the trajectory only when verified and shorter in native steps. |
| `features.motion_execution_mode` | `resampled` | Official actor and benchmark runs use `resampled` unified actions; `feedback` is restricted to trusted legacy fixed-input diagnostics, requires `motion_review=false` and `tracking_guard=false`, and is rejected prior to benchmark launch. |

`feedback` motion execution mode is reserved exclusively for trusted Python diagnostics such as `scripts/probes/feedback_motion_probe.py --mode feedback`; it does not support the public `robot_action` tool and cannot be used for unified dual-arm manipulation by the actor or programs. Both `Config.validate_launch()` and the evaluation queue reject `feedback` mode before launching models or workers for a benchmark. Non-benchmark diagnostic workbenches may pass `--motion-execution-mode feedback --no-motion-review --no-tracking-guard`, though this does not expose public arm action tools; historical archives recorded in `feedback` mode remain readable and replayable. In `feedback` mode, the worker plans once per waypoint, selects the closest $2\pi$-equivalent joint target within limits (verified for full-link URDF equivalence and target pose accuracy), and repeatedly issues commands through the native `take_action` entry point until position error is within the requested tolerance, orientation error is at most `0.1 rad`, and all active-arm joint velocities are at most `0.1 rad/s` for two consecutive native steps. If neither best position/orientation error nor joint target error improves sufficiently over 15 native steps, execution stops with `feedback_stalled` regardless of instantaneous velocity (which also bounds cases where position is reached but velocity fails to settle); each action remains bounded by 10 seconds of simulated time (default 250 native steps), the action wall-clock deadline, cancellation, and native terminal conditions without altering the episode's official step limit.

`feedback` mode preserves sequential user waypoints and `after_motion` gripper dwell times while explicitly rejecting cached trajectory previews and `during_motion` fractional gripper timing. Because closed-loop feedback tracks the planned endpoint rather than following the initial open-loop trajectory verbatim, collision checks performed during initial planning do not guarantee a collision-free execution path. `reference_resampled_steps` provides only a diagnostic estimate based on initial trajectory row counts, whereas actual step accounting always uses `executed_native_steps` from the receipt. Step accounting for `robot_wait` and joint policy prefixes is unchanged.

In controlled comparisons on RoboDojo bottle manipulation tasks, `feedback` mode reduced step counts on short-horizon motions but did not improve full-task success rates; the comparison surfaced a stall-detection gap under high instantaneous velocity and long-windup joint targets, both of which have since been fixed. `feedback` mode is retained solely for trusted fixed-input diagnostics, while official unified actions default to and require `resampled`.

Whether a tool is enabled in configuration and whether the model chooses to call it are separate questions. `features.disabled_tools` filters the model's tool catalog, direct actor calls, and `program_run` broker calls simultaneously. Physical actions initiated from inside a program pass through the exact same `robot_action` execution boundary and approval workflow and cannot bypass them via legacy action names. Disabling `program_run` or individual tools is never a substitute for validating native observation and execution protocols.

Depth sensing is disabled by default across native capture, model tools, programs, and history queries. For the three explicit RGB-D feature flags, numeric interfaces, and skill parameters, see [RGB-D Numeric Tools](rgbd-numeric-tools.md). The public `depth_query` tool is exposed only under the `rgbd_proprio_calibrated_v1` profile (legacy `depth_move` was removed in the 2026-10 refactoring), and adding `depth_query` to `disabled_tools` also disables the depth alias on `geometry_query`. Combining any depth feature flag with a non-RGB-D observation profile raises a configuration validation error at startup.

### State-Aware Completion Guidance (`HomePoseCheck`)

`completion_guidance="hook"` or `"both"` uses the [`HomePoseCheck`](../../ni_rua/runtime/actions/home_check.py) component. At the start of each episode—after native reset and scene settling, and before the first actor action—`HomePoseCheck` records the measured `ee_pose` of every arm (ARX X5: dual-arm, `link6` position and `quaternion_xyzw` orientation in the `env_origin` frame; SO-101: arm `right`, `gripper_frame_link` in `so101_base`; the identity comes from the run's `EmbodimentProfile.home_check`) from the first public observation. This initial reference is preserved in observation history and the home reference record without being overwritten by subsequent observations, and is re-recorded only when an explicit environment reset or session resume starts a new episode. New benchmark runs default to `hook`, which neither injects an upfront home-pose reminder into the initial prompt nor sends unconditional home-pose warnings on every turn; non-benchmark development runs do not trigger benchmark turn continuation. Resumed and replayed runs honor their archived setting (defaulting to `none` for legacy archives lacking the field).

When the primary actor emits `turn.completed`, the native episode has not ended, and standard scheduling guards permit continuation, `HomePoseCheck` compares the latest complete observation against the recorded initial pose using RoboDojo's default `all_robot_back_to_origin` geometry rule: the absolute difference along every Cartesian position axis for both arms must be **at most 0.15 m**, and the shortest quaternion rotation angle must be **at most 20 deg** (inclusive at the boundary). Quaternions `q` and `-q` represent the same orientation, and full-turn joint windup and gripper aperture are ignored. While this matches the terminal home condition of arrangement tasks, it does not represent the complete success criteria of every task; verify task-specific homing conventions before relying on it for other task families.

| Check Outcome | Continuation Prompt Sent |
| --- | --- |
| `away`: valid dual-arm measurements exist and at least one arm exceeds tolerance | Explicitly reminds the model that the arms have not returned to the initial pose, provides the history reference to the initial observation, and notes that other task conditions may also remain unmet. |
| `home`: both arms are within tolerance | Sends the standard continuation prompt ("The task is not finished yet; please continue."). |
| `unknown`: missing initial/current measurements, stale observation, mismatched identity/frame, or invalid data | Sends the same standard continuation prompt without diagnosing missing evidence as an unhomed robot. |

`HomePoseCheck` reads only permitted robot-state artifacts—it never issues actions, automatically resets the arms, or queries the private evaluator or object ground truth. Admitting any physical action invalidates the current observation evidence; intermediate progress snapshots cannot substitute for a terminal observation, so only a complete post-action terminal capture or a subsequent `robot_observe` restores a valid check state. While the simulation is paused, the same complete observation can be checked repeatedly, and read-only `history_*` queries do not alter the active observation evidence. Native terminal states, cumulative model request budgets, timeouts, unconfirmed actions, and active program guards always take precedence over the continuation hook.

Each episode logs a `completion_guidance.home_reference` event recording the initial reference pose, while the manifest and task-prompt configuration record the policy version, tolerances, initial reference, and the three prompt templates. Every continuation attempt logs a `benchmark.actor_turn_continuation` event containing the check outcome, per-arm errors, initial and current observation references, `continuation_kind`, and the exact prompt selected. Note that this event records the initiation of a continuation turn; verify subsequent session messages to confirm upstream delivery. Under state-aware `hook` mode, the static `continuation_prompt` field is `null`—inspect `continuation_prompts` and the per-turn events instead.

For example, launching a benchmark with the default state-aware `hook` requires no extra flags:

```bash
mamba run -n ni-rua python -m ni_rua.apps.gateway --benchmark --task arrange_largest_number_random \
  --run-dir runs/arrangement-home-check
```

Pass `--completion-guidance none` to disable home-pose checking, or `--completion-guidance both` to also include the initial prompt reminder. Queue manifest cases inherit the unified configuration (`hook` by default) when the field is omitted, and can override it per case with `"completion_guidance": "none"` or `"both"`.

All existing CLI flags remain supported alongside their negated counterparts, including `--no-default-task-notes`, `--no-vision-compare`, `--no-enable-wait`, `--no-pi05`, `--no-tracking-guard`, `--no-joint-replan`, `--no-motion-review`, `--no-terminal`, `--no-record-video`, and `--no-export-video`. `--no-visual-review-model` disables an auxiliary review model enabled in a config file. Passing `--disabled-tools robot_wait vision_review` replaces the disabled tool list, while passing `--disabled-tools` with no arguments clears the list (it never force-enables tools that are unavailable due to feature flags or observation profiles).

### Optional View Tools

`robotic_view` and `stereo_guide` are independent boolean flags that both default to `false`. Either tool can be enabled on its own:

```json
{
  "version": 1,
  "features": {
    "robotic_view": true,
    "stereo_guide": false
  }
}
```

Gateway CLI flags `--robotic-view` / `--no-robotic-view` and `--stereo-guide` / `--no-stereo-guide` override the configuration file. Individual cases in a queue manifest can explicitly override `"robotic_view": true` or `"stereo_guide": false` (inheriting the unified configuration when omitted; neither field accepts strings or `null`). Session resumption and replay honor the archived flags, treating missing fields in older archives as `false`.

When disabled, the corresponding plugin is not registered and neither the tool nor its documentation is delivered to the actor or programs. Even when enabled via feature flags, passing `--disabled-tools robotic_view stereo_guide` can still suppress them by name. Tool documentation is delivered exclusively through each tool's `ToolSpec` without modifying global task prompts or Task Notes, and neither tool moves the robot, captures new observations, or infers task success. For parameter schemas and usage examples, see [Wrist View Solver](robotic-view.md) and [Stereo Epipolar Guide](stereo-guide.md).

## Remote GPU Services (`remote`)

The optional `remote` section names an SSH host and the services on it (for example the VGGT/SAM 3.1 perception service). When `remote.enabled` is `true`, the gateway (and `python -m ni_rua.apps.remote --config <file>`) opens the SSH forwards, reuses a healthy service or starts it detached on a GPU with enough free memory, keeps health available at `GET /v1/remote/status`, and on exit closes the forwards and, only with `remote.stop_on_exit`, stops the services it started. It is disabled by default, an unused section is omitted from exported config snapshots (so X5, simulation and frozen-checkout queue projections are unchanged), and `--remote` / `--no-remote` override `remote.enabled` for one run. `features.vggt_endpoint` must be the local end of a forward declared in `remote.services`. Field meanings, units, defaults, the start/reuse/stop rules and the status shape are in [SO-101 integration, section 9](so101-integration.md#9-distributed-deployment-mac--remote-linux-gpu-server); a ready-to-merge example is `configs/so101.remote.example.json`. The SO-101 cuRobo IK service is a second entry (`name` `curobo_ik`, `remote_port` 8341, `workdir` the deployed `services/curobo_ik` directory, `command` `bash start.sh`, `stop` `bash stop.sh`, `health_path` `/health`, `gpu` `auto`; example in [SO-101 integration §12.3](so101-integration.md#123-the-service-and-how-the-gateway-starts-it)) that the deployment's `ik_service.url` points at. None of it enters model context.

## Agent Backend (`agent`)

### Evidence helpers (`agent.evidence`)

`RelayEvidenceClient` ([`ni_rua/cortex/agents/evidence.py`](../../ni_rua/cortex/agents/evidence.py)) answers one evidence packet with one fresh, streamed, tool-free request through the run's own model relay: no agent process, home directory, history or memory. It takes the same keywords and `review_evidence(...)` call as `CodexEvidenceAgent` and raises the same error strings, so `VisualReviewer` and self-briefing run unchanged and keep validating the answer schema themselves. Because the request goes through the relay, it uses the shared 180-call budget (charged only for a delivered usable answer), attribution (`source` is `sol_visual_review` or `self_briefing`, the thread is `evidence-<request_id>`), retries, the transport-recovery gate, the blocked-transport gate and the egress scrub. Self-briefing always asks the actor's model on the actor's upstream. Visual review asks `features.visual_review_model` on the `"evidence"` binding when `agent.evidence.upstream` is set, else on the actor's upstream; a non-Codex backend whose actor wire is not `openai_responses` refuses to launch with `visual_review_model` unless `agent.evidence.upstream` is set (`evidence_upstream_required_for_visual_review_model`). Before the first benchmark that enables an evidence feature on a new (upstream, model) pair, the user must authorise one live probe that the provider accepts the structured-output request; until then a rejection is an ordinary recorded failure (visual review raises to the tool, self-briefing is skipped), never a silent fallback.

Fairness rule: the default keeps Codex on `CodexEvidenceAgent`, so existing Codex experiments stay comparable with their history. A harness comparison whose arms enable `self_briefing` or `visual_review_model` must set `agent.evidence.client="relay"` on its Codex arm. The effective client is recorded as manifest `evidence_client` (only written when an evidence feature is on) and `agent_backend.evidence_client`; the queue writes a `comparison_evidence_path_mismatch` warning to `state.json` (`warnings`) and `events.jsonl` (`queue_warning`) when one manifest's evidence-enabled cases use different clients. Switching Codex from native to relay is its own single-variable change: the relay request carries no Codex harness context and names its format `evidence_answer` (Codex sends `codex_output_schema`, `text.verbosity` and `reasoning.context`). The default `agent.evidence` section is omitted from snapshots, and a frozen checkout without `EvidenceConfig` rejects a non-default one with `unified_config_incompatible:agent.evidence`.

`upstream` fields: `source` (`profile`: an NI-RUA provider profile named by `settings`; the profile owns the key and writes `wire_api`, `base_url`, `auth_scheme`, `provider` = the profile id and the compat fields when the config is loaded, so `effective_config.json` shows the concrete endpoint and never the key, and the launch gate refuses a configuration that no longer matches its profile with `profile_upstream_stale`, a profile without key with `profile_missing_key`, and a wire whose credential header the relay does not forward, e.g. `x-api-key` on `openai_responses`, with `profile_auth_scheme_unsupported`; or the older `explicit`, `codex_home`, `claude_settings` for Claude Code: endpoint, key and forwarded provider variables from the official settings file named by `settings`, or `opencode_config` for OpenCode: endpoint, key and wire from the official OpenCode config file named by `settings`, entry selected by `provider`; see [Agent Backends](agent-backends.md#configuration-per-backend)), `wire_api` (`anthropic_messages`, `openai_responses`, `openai_chat`), `base_url` (http(s) URL without credentials, query or fragment), `api_key_env` (the NAME of the environment variable holding the key; the value is never stored in the config, manifests or queue records), `auth_scheme` (`bearer` or `x-api-key`) and `provider` (a label for price cards and resume identity). In the queue, a case may set `agent_backend`, `model` and `effort`; a frozen checkout whose config schema has no `AgentConfig` rejects `agent_backend` cases with `unified_config_incompatible:agent` rather than running them as Codex. Experiment-library group conditions and report conditions expose `agent_backend` (`codex` for archives that predate the section). Mixed-backend comparisons (Codex, Claude Code and OpenCode cases in one manifest, e.g. one `experiment_condition` per backend) record the backend as an explicit condition at every level; the additional fields are listed in the table below.

`claude_code` launch gate and runtime (`cortex/agents/factory.py`, `cortex/agents/claude_code/session.py`): besides the shared refusals (`features.lean_projection`; `features.visual_review_model` without a usable evidence upstream; `model.effort` must be `low`, `medium`, `high`, `xhigh` or `max`; `features.sandbox_enabled=true` is accepted, see [Code Execution Sandbox](#code-execution-sandbox)), the launch is refused with `claude_code_upstream_requires_anthropic_messages` unless `agent.claude_code.upstream` is a profile serving `anthropic_messages`, a `claude_settings` file, or an explicit `anthropic_messages` endpoint with `base_url` and `api_key_env`, and with `agent_backend_unavailable:claude_code: <reason>; install ni-rua-harness[claude]` unless `claude-agent-sdk==0.2.180` is installed and the CLI (bundled, or `cli_path`) reports `2.1.321` (one `--version` run in an empty temporary home). At start the gateway reads the key from the named environment variable (`claude_code_upstream_key_missing` when unset); the CLI itself only sees a placeholder key and the run-local relay and MCP endpoints. A resumed run is gated against its archived configuration (not the invocation's) and must match the recorded `runtime/agent` identity (backend, session id, isolation, tool digest, model, provider, counting, wire, SDK and CLI versions) and still hold the CLI session history under `private/claude-config`; a resume after an unclean exit invalidates the model context epoch and schedules the decision reminder. `apps/evaluation/checkpoint.py` and `turn_probe.py` refuse non-Codex archives (`checkpoint_requires_codex_archive:<backend>`); a replay viewer of a Claude Code archive needs no runtime. Model changes from the operator console (`set_model` / `apply_agent_settings`) apply before the next prompt (the CLI first sends one charged `max_tokens: 1` validation request through the relay; a refused change keeps the previous model); effort changes apply from the next session start, which the console reaches with a handoff (`handoff_run`, a successor run). A native turn the CLI starts by itself while the NI-RUA turn is over (a background shell or monitor finishing, a scheduled wake-up) is adopted as an NI-RUA turn (`agent.turn_started {origin: "native_wakeup"}`, `capabilities.native_wakeup`); its tool calls carry that turn id, a `run_turn` during it joins it, and the console `prompt` command waits for it to end like any running turn. Registry tool calls outside a running turn are refused; with `agent.claude_code.subagents` enabled, `context_delivery` is no longer forced to `full` (subagent calls run in `isolated` full-delivery mode while the main chain follows `agent.claude_code.context_delivery`, which defaults to `delta` with `full` available as an explicit opt-out and is recorded as `agent_backend.context_delivery_policy`).

`opencode` launch gate and runtime (`cortex/agents/factory.py`, `cortex/agents/opencode/session.py`): besides the shared refusals, the launch is refused with `opencode_upstream_wire_unsupported:openai_chat` (the relay serves OpenCode only on `anthropic_messages` and `openai_responses`), `opencode_upstream_incomplete` unless an explicit upstream names `wire_api`, `base_url` and `api_key_env` (or uses `source: "codex_home"`, which implies `openai_responses` and reuses the Codex credential source of `model.codex_home`), and `agent_backend_unavailable:opencode: <reason>` unless `agent.opencode.executable` is an absolute executable whose `--version` prints `opencode v2.2.7` (install: download the npm tarball `@opencode/cli-<target>@2.2.7`, `<target>` one of `darwin-arm64`, `darwin-x64`, `linux-x64`, `linux-x64-baseline`, `linux-arm64`, and extract `package/bin/opencode` to `~/.local/share/ni-rua/opencode-2.2.7/opencode`; not the curl installer, not on `PATH`). NI-RUA runs the binary only as `serve` and as the TUI with `--server`; any other subcommand would start a detached background service. At start the session also requires `GET /api/info` to answer 200 with version `2.2.7` (it answers 503 while starting), the `GET /openapi.json` route list to equal the checked-in `opencode_routes.json` (170 operations), `GET /api/model` to list exactly the declared relay models with their limits, input modalities and effort variants (`opencode_served_models_mismatch`), and `rg` on the host; `agent_backend.native_tools.enabled` records the native tool names of the first model request with tools that the relay forwarded (2.x has no tool-listing route). `opencode serve` runs on a free loopback port with a per-run `OPENCODE_PASSWORD`, its own private XDG directories and one read-only config dir (`private/opencode/xdg/config/opencode`, which is both `OPENCODE_CONFIG_DIR` and `$XDG_CONFIG_HOME/opencode`) holding the generated `opencode.json`: `relay` is the only usable provider (`provider.use` policies), permissions are `read * allow` plus a deny of `webfetch`, `websearch` and `question` (and `subagent` when `agent.opencode.subagents=false`), `experimental.todo: true` keeps the todo tool, the `ni_rua` MCP server has Code Mode off (registry tools stay direct `ni_rua_<tool>` calls) and `media.image.auto_resize: false` stops OpenCode re-encoding tool-result images. A model selected during the run is declared by rewriting that file atomically (OpenCode reloads it within about 0.3 s); only declared models can be used, so the subagent `model` parameter cannot leave the run's recorded models. A turn is admitted when `POST /api/session/{id}/prompt` answers 200 with the user message id, which is the turn boundary (a 4xx is a definite rejection and restores the previous turn; a 5xx, timeout or dropped connection is unknown admission and disconnects, never retried). The turn ends at the last `idle` message after that boundary while no session of the private server is active and the inbox is empty, decided from `GET /api/session/active`, `GET /api/session/{id}/inbox` and every page of `GET /api/session/{id}/message`, never from `/api/event` alone (the stream has no replay; every gap is reconciled, and a watchdog reconciles every 10 s while a turn runs); a turn with subagents needs the same quiescent snapshot twice 0.5 s apart, and a session that stays idle without a terminal answer fails the turn with `opencode_turn_incomplete`. Operator steers join at the next step boundary. An interrupt (also with no host turn while the main session is busy, and after an unknown admission while the server lives) first blocks the relay for the main session and every known subagent session (cancels in-flight calls and denies new ones until the next turn), then calls `POST /api/session/{id}/interrupt` on the main session (synchronous, cascades to foreground subagents) and on every subagent session still active. A permission request is answered `reject` at once (`agent.permission_auto_rejected`; the generated config has nothing to ask) and the turn then fails `opencode_permission_rejected`. A background subagent keeps the turn open while it runs, and a native execution that starts while no host turn runs (a background subagent's or shell's completion report) is adopted as an NI-RUA turn (`agent.turn_started {origin: "native_wakeup"}`, `capabilities.native_wakeup`); a `run_turn` during it joins it. `model.effort` is the reasoning effort on both wires: every declared relay model declares one `variant` per tier as an explicit request-body fragment, selected through the session's model ref (`{id, providerID: relay, variant}`). `anthropic_messages` accepts `low`, `medium`, `high`, `xhigh`, `max` (request body `thinking: {type: adaptive}` plus `output_config.effort`; `thinking.display` only when `agent.opencode.thinking_display` is set); `openai_responses` accepts `none`, `minimal`, `low`, `medium`, `high`, `xhigh` (`reasoning.effort`; the provider package also sends `store: false` and `include: [reasoning.encrypted_content]`). Another value refuses the launch with `agent_effort_unsupported:opencode:<effort>`. The mapping is the identity (no per-model table): a tier the model rejects fails at the provider. `set_effort` applies from the next turn. Provenance: `agent_backend.native_effort = {variant, body, thinking_display, declared_variants, wire_field}`, `agent_backend.effective_limits = {context, output, source}` of the current model and `agent_backend.declared_models` (`{id, limits, input}` per declared model). OpenCode sends `limit.output` as `max_tokens` / `max_output_tokens`; Claude Code sends up to 128000 on its own, a recorded harness difference. `set_model` accepts any model id: an undeclared one is declared first (atomic config rewrite, hot reload within about 2 s, else one `POST /api/location/reload`, else `opencode_model_declare_failed:<id>` with the selection unchanged), and the native session is switched with `POST /api/session/{id}/model` only at the start of the next host turn, never mid-turn. With `agent.opencode.subagents=true` (the default), `context_delivery` is no longer forced to `full` (child sessions run in `isolated` full-delivery mode while the main chain follows `agent.opencode.context_delivery`, which defaults to `delta` with `full` available as an explicit opt-out and is recorded as `agent_backend.context_delivery_policy`) and child sessions are followed: their transcript rows carry the child session id and `parent_item_id` = the `subagent` tool row, and are never final-answer text. Resume requires the recorded identity (backend, session id, isolation, tool digest, model, provider, counting, wire, CLI version) and the session in the run's OpenCode database (a 1.19.5 run is refused with `resume_agent_identity_conflict:cli_version`, while its archive still opens for replay); an unclean previous exit invalidates the model context epoch. A disconnect also blocks the relay for those sessions, and a steer after an interrupt is refused (`turn_interrupt_requested`). Close interrupts whenever the server lives (a busy main session makes the close unclean), stops the server's process tree including every detached shell group seen while it ran (re-snapshotted every 2 s), and verifies that none survives; after a server crash the teardown is reported unconfirmed. The full runtime description, a complete example config and the install steps are in [Agent Backends](agent-backends.md#opencode-runtime-opencode-serve-227).

## Evaluation Queue, Experiment Library, and Standalone Workflows

`scripts/benchmark_queue.py --config ...` uses the same unified configuration file for both queue scheduling and per-case gateway runs. The queue manifest still defines the list of cases to run, and explicit per-case fields in the manifest can override specific experimental conditions while omitted flags inherit from the unified configuration. At startup, the queue writes `effective_config.json` for auditing and OOM retries so subsequent edits to configuration files on disk never alter an active queue's conditions. Similarly, `scripts/benchmark_group.py --config ...` embeds the resolved configuration directly into the generated queue manifest.

Each manifest case may include an optional non-empty string `experiment_condition` to label its experimental group; this field is preserved in the queue manifest and `state.json` strictly for experiment library grouping and is never passed to gateway CLI flags, runtime configs, or model context.

During preflight, the queue statically parses `ni_rua/core/config.py` in each target frozen runtime checkout without executing target code. Audited backward-compatible differences—where an older frozen checkout predates newly added configuration fields (`features.sandbox_enabled`, `robotic_view`, `stereo_guide`, `lean_compact`, `queue.eligible_gpu_indices`, motion threshold fields, external perception fields, and the `analysis` section)—are handled automatically: when those fields equal their current class defaults (such as `sandbox_enabled=false` or `eligible_gpu_indices=null`), the per-case launch snapshot omits the unknown keys and records the projection in `manifest.config_compatibility` inside `config.json`. If any new field is set to a non-default value or an unaudited schema difference is detected, the queue rejects the manifest before GPU admission. The queue manifest retains the complete unified configuration snapshot, and OOM recovery validates the exact same compatibility projection.

Official benchmark budgets cannot be overridden by the queue, and OOM retries trigger only when native OOM evidence and process cleanup are both confirmed—writing each retry to a fresh directory while preserving all failed attempts.

You can dynamically update the concurrency ceiling of a running queue:

```bash
mamba run -n ni-rua python scripts/benchmark_queue.py --output /path/to/running-queue --set-max-parallel 15
```

This command atomically updates `control.json` (`{"max_parallel": 15}`) inside the target queue directory without reading current configuration files or launching tasks; it accepts only positive integers and rejects terminated queues or legacy queues that predate `control.json`. The scheduler reads `control.json` before every poll cycle and before every case admission: raising `max_parallel` triggers an immediate admission check on the next loop iteration without waiting for the 90-second GPU sampling interval, whereas lowering `max_parallel` never kills active cases and simply pauses backfilling until active runs drop below the new ceiling. GPU memory reservations and shared lease rules still apply. Invalid or unreadable `control.json` files are ignored while retaining the previous limit and logging `queue_control_invalid` once per distinct consecutive error.

The CLI prints `requested` once `control.json` is written; confirm actual application via `state.json.scheduling.max_parallel` and the `max_parallel_changed` event in `events.jsonl` (which records the old value, new value, and active run count at the time of change). The initial `manifest.json`, `config.json`, and `effective_config.json` remain immutable startup snapshots while runtime scheduling adjustments are tracked in `state.json` and `events.jsonl`. Queue processes started from older code require restarting under the current entry point to support live `control.json` updates.

`scripts/motion_review_eval.py prepare --config ...` inherits the model, reasoning effort, provider home, machine paths, and image settings from the unified configuration, freezing the resolved configuration into the paired evaluation protocol and generated queue manifests; summary aggregation verifies the saved configuration rather than reading current defaults, and previously generated `gpt-6-astra` protocols continue to use their recorded model and effort.

In `scripts/reference_episode.py`, both the direct API client and the robot backend share a single resolved `Config` instance; `--config`, `--model`, `--effort`, and `--codex-home` can override settings explicitly, and `--print-config` prints the effective configuration without reading credentials or launching the model or robot. New reference runs default to `~/.codex` with `gpt-6.1-sol` / `high`, sending the model name, `reasoning.effort`, and `service_tier="default"` in each request. Because this standalone client calls the upstream API directly without the Codex app-server, it reads credentials strictly from the selected provider's declared `env_key`, its bearer token configuration, or the API key in the selected home's `auth.json`—it does not support interactive ChatGPT web login tokens and never falls back to `OPENAI_API_KEY` in the environment unless `env_key` explicitly declares it. Missing providers, endpoints, or credentials fail fast before any model request is sent.

## Resumption, Replay, and Reproducibility

Every run archive saves the complete resolved configuration alongside legacy manifest fields so older analysis scripts continue to work. The saved snapshot captures the full effective runtime conditions rather than just the partial overrides supplied by the user.

When resuming or replaying an existing run, experimental semantics are restored strictly from the archive rather than reading current default files on disk (while local service parameters such as the HTTP listening port can still be changed). Legacy manifests lacking `enable_wait` keep it `false`, those lacking `vision_compare` keep it `true`, those lacking `actor_payload_profile` default to `full_v1`, and those lacking `default_task_notes` keep it `false`. A snapshot or manifest written before the reply-delivery settings existed restores them as absent (`budgeted_action_reply`, `reply_same_as`, `reply_float32`, `reply_static_once`, `reply_compact_encoding` `false`, `action_reply_profile` `full`; `REPLY_DELIVERY_ABSENT`), and one written before the catalogue settings existed restores `tool_catalog_profile` as `full_v1` and `robot_urdf_delivery` as `inline` (`CATALOGUE_DELIVERY_ABSENT`; both sets are `FEATURE_ABSENT_VALUES`), so a resumed or replayed run keeps the form it ran with; each key is restored on its own (an archive that records `tool_catalog_profile`, which is older, but not `robot_urdf_delivery` keeps its profile and gets `inline`), and a snapshot that states a key keeps what it states. The evaluation queue applies the same values when it projects a configuration onto a frozen checkout that lacks the fields: only the absent values may be left out for it, the current defaults fail closed; for a checkout that has `tool_catalog_profile` or `robot_urdf_delivery` but lists choices without the requested value, the queue stops with `unified_config_incompatible:features.<field>=<value>` instead of sending or dropping it. Checkpoint slices (`turn_probe`) restore the same values. A configuration object that is missing altogether (a test double of a runtime) publishes the prose `full_v1` catalogue; every Harness holds a configuration. Unified configuration snapshots from before `default_task_notes` or `vision_compare` were introduced likewise restore their respective historical defaults. Task Notes always reuse the exact archived body, source, and version without regenerating or re-appending current default notes. Legacy image settings lacking `reuse_exact_images` keep it `false`, and those lacking `trim_max_inline_images` restore `0` (byte-size trimming only). If an archived model request ledger has no `transport_recovery` record, automatic transport recovery remains disabled on resume; otherwise, it resumes under the recorded policy. Remember that `--resume` creates a fresh simulator episode/generation rather than restoring mid-episode physics state, while preserving cumulative thread budgets and token accounting.

Consequently, changing a default setting in `configs/ni-rua.json` affects only newly launched runs. To run a controlled paired ablation, create two fresh run directories, save their respective resolved configurations, and verify the actual tool catalog and observation profile in each `manifest.json`—never assume historical runs automatically migrated to newer defaults.

## Fixed Runtime Protocol and Boundaries

The constants and capability boundaries below are intentionally fixed in code rather than exposed as arbitrary JSON configuration toggles, ensuring that editing a config file cannot inadvertently alter benchmark rules or violate the actor information boundary:

| Scope | Fixed Protocol Rule |
| --- | --- |
| Official model budget | `180` delivered valid actor / helper / compaction responses per episode; no hard per-request wall-clock timeout; explicitly retryable upstream API errors are automatically retried with backoff by `Harness` up to `12` times (with SDK-internal retries set to `0`), followed by bounded cooldown resends governed by `model.transport_recovery` (see [Model-Led Operation](model-led-operation.md)); failed or incomplete attempts are accounted separately. |
| Official run supervision | `900`-second environment initialization deadline; during an active run, stops only after `1,800` consecutive seconds with zero model, program, robot, or simulator activity; no whole-episode wall-clock cap on official benchmarks. |
| Decision boundaries | No artificial cap on read-only tool queries between physical actions; completing a model turn does not terminate the native episode. |
| Native actions | Per-task native step limits, task success criteria, and control frequencies are governed by RoboDojo, with a single physical action writer and idempotent receipts. |
| Unified action schema | `robot_action` accepts `1`–`32` stages per batch (up to `16` stages per arm); dual arms execute along a shared timeline with intra-arm ordering, cross-arm dependencies, and `observe` checkpoints enforced by the batch contract. `robot_wait` and policy prefixes execute at most `50` native steps per call, and action timeouts are bounded to `0.1`–`300` seconds. |
| Legacy atomic actions | Legacy single-arm `EEAction` requests support at most `8` sequential waypoints for trusted compatibility callers only and do not restrict `robot_action` batches. |
| Motion review contact diagnostics | Final continuous approach window is within `60 mm` / `20 deg` of the stage goal; placement contact allows up to `3 mm` geometric penetration tolerance (`2 mm` default), reporting numerical risk without blocking execution while preserving raw overlap facts. |
| Tracking guard | Triggers when joint tracking error exceeds `0.5 rad` for `5` consecutive native steps, halting without automatic trajectory modification. |
| Joint replanning | Attempted only when at least `15` seconds of action timeout remain, substituting a candidate trajectory only if it is fully validated and shorter in native steps. |
| Program resource limits and budgets (enforced in both sandbox modes) | `1 GiB` address space, `8 MiB` file size limit, `128 KiB` source code limit; per-program active wall-clock budget defaults to `180` seconds (maximum `300` seconds), excluding wait time for auxiliary model calls and primary-model action approval; no cap on tool call counts; single-threaded numerical libraries and a `5`-second safety margin for action admission. |
| Standalone scene service limits | Maximum `32 MiB` per blob; per-job queue and wall-clock budgets default to `30` seconds each (validated per request), while worker count, queue depth, and total blob storage are configured under `scene`. |
| Native Codex capabilities | Native dynamic tools return text and images directly, with optional local tool search loading registered tools on demand; shell, file operations, and native memories are enabled while web search and external extensions are disabled. OS namespaces and `program_run` Landlock/seccomp isolation are governed by `features.sandbox_enabled`, and native thread admission restricts robot tool calls strictly to the primary actor thread. |
| Autonomous execution | Startup instructions require the primary model to decide plans, parameters, and program action approvals autonomously without asking a human operator; native user-input requests immediately receive empty answers, command/file approvals on the active session automatically return `acceptForSession`, and requested permissions are granted at session scope without human intervention. Harness observation projection and action admission remain enforced at all times, and Landlock is active when `features.sandbox_enabled=true`. |
| Observation permissions | Native depth is forbidden by default and permitted only under the explicit RGB-D profile; hidden object poses, contact ground truth, and private evaluator state are forbidden across all profiles. |
| Video timing | Three-camera recording samples at `5 Hz` in simulation time plus observation boundary frames, preserving the exact non-uniform frame mapping rather than recording at the full native physics rate. |
| Stopping and scoring | Unconfirmed stops, `unknown` action outcomes, and infrastructure failures remain unscored under the scoring policy and can never be configured to fabricate task success or hide failures. |

Direct tool mode is pinned via a per-run private `model_catalog_json` that preserves the native model catalog from Codex SDK/CLI `0.160.0` while setting `tool_mode` to `"direct"` (because native model metadata overrides feature flags, disabling `code_mode` alone is insufficient). Model names, reasoning effort tiers, context windows, and other capabilities remain unchanged; for catalog provenance, checksums, and upgrade procedures, see [`third_party/codex/README.md`](../../third_party/codex/README.md).

If future research requires experimentally varying any of these fixed protocol constants, introduce an explicit versioned configuration field with validation, manifest logging, and regression tests, and clearly separate official benchmark runs from exploratory development runs.

For `--benchmark` and `--exit-after-turn` runs (interactive development workbenches do not auto-exit on idle), runtime supervision measures inactivity from the most recent genuine activity: initiating a model request, receiving real upstream transport bytes, emitting code execution events/output, or advancing robot/simulation execution all reset the 30-minute (`1,800`-second) inactivity timer. Merely having a pending request, synthetic keepalives, runtime status heartbeats, or live child processes does not reset the timer. As long as any subsystem makes genuine progress, the episode is never terminated for total elapsed wall-clock time; if all subsystems remain silent for 1,800 seconds, active requests are cancelled and the run enters the stop and resource-cleanup sequence, recording `runtime_inactivity_timeout` as an unscored infrastructure interruption. Explicitly retryable API errors are retried automatically by `Harness`; once immediate retries are exhausted or an upstream transport disconnect occurs—and provided no physical action is in flight or unconfirmed and no program is active—the proxy cools down and resends the identical request according to `model.transport_recovery`, terminating only on non-retryable errors, rejected recovery gates, or exhausted recovery budgets. See [Model-Led Operation](model-led-operation.md) for details.

Reaching the 900-second environment startup deadline closes action admission and initiates resource cleanup, though it does not guarantee that the entire gateway process will exit within 900 or 905 seconds. [`RuntimeSupervision`](../../ni_rua/runtime/supervision.py) retains ownership of the startup task while [`Workbench`](../../ni_rua/apps/gateway/workbench.py) polls published robot worker, SDK bridge, app-server, and terminal subprocess handles every 50 ms (including processes spawned after the stop request was issued), sending `SIGTERM` first and escalating to `SIGKILL` after 5 seconds while recording signal and exit evidence.

In [`RobotProcess`](../../ni_rua/robot/backends/robodojo/robot_process.py), a single request deadline covers acquiring the write lock, writing to the pipe, sending cancellation, and awaiting the worker response; partial writes or missing receipts remain `unknown` without automatic action replay. After a pipe failure, planned robot close waits total at most 27 seconds, whereas a standard close takes at most 237 seconds across the worst-case branch (covering the close RPC, process exit, and reader thread join). These bounds exclude OS scheduling delays or uninterruptible kernel I/O; Python or native threads that cannot be terminated safely remain owned by their respective objects rather than being falsely logged as released. Enforcing a hard whole-process exit deadline requires an external process supervisor. For CPU subprocess regression tests, see [`test_robot_process_deadline.py`](../../tests/robot/robodojo/test_robodojo_motion_runtime.py) and [`test_runtime_shutdown.py`](../../tests/runtime/harness/test_harness_lifecycle_and_shutdown.py).

`features.arm_queue` and `features.motion_cost_preview` are enabled by default and can be overridden via `--[no-]arm-queue` and `--[no-]motion-cost-preview`. Both require `resampled` execution mode, and `motion_cost_preview` additionally requires a calibrated observation profile. Disabling `arm_queue` also rejects raw `ArmQueueAction` calls, and disabling `motion_cost_preview` also rejects corresponding program calls. Queue manifests may specify `eligible_gpu_indices` as a list of unique non-negative GPU indices; when omitted, all visible GPUs remain eligible for automatic admission, and when set, excluded GPUs are never selected while eligible GPUs still obey shared GPU leases and memory checks.

## Bounded Continuation, Execution Checks, and Manipulation Evidence

Four independent boolean flags under `features` default to `true` for new runs, controlled via CLI flags `--[no-]bounded-continuation`, `--[no-]motion-safety-guard`, `--[no-]trajectory-preview`, and `--[no-]manipulation-protocol` (and matching snake_case fields on queue manifest cases). When resuming or replaying legacy manifests that lack these fields, they default to `false` to preserve historical behavior:

- `bounded_continuation`: The first completed `final` answer establishes a baseline; thereafter, if no physical action progress occurs, the episode terminates after `3` consecutive `final` answers with no new tool evidence or after at most `6` recovery `final` turns in total (native episode termination always takes precedence). New read-only tool exploration grants only bounded recovery turns, and the private evaluator score is never consulted to make this decision.
- `motion_safety_guard`: Inspects compiled joint trajectories prior to execution for abnormal joint detours/windup and remaining native step budget; if rejected, returns diagnostic evidence without altering joint commands or auto-replanning while preserving already executed step counts.
- `trajectory_preview`: Attaches candidate joint configurations, public forward-kinematics poses, and synchronized dual-arm model clearance distances to motion cost previews, and enables `robot_action(mode="inspect")` to query trajectory states at specific native steps or project them onto current RGB images. Uses strictly the public robot model, measured joint feedback, public calibration, and candidate commands—never task object ground truth (see [Motion Safety and Trajectory Evidence](motion-safety-and-trajectory-evidence.md)).
- `manipulation_protocol`: Aligns Task Notes, `task_plan`, and bounded templates around explicit contact locations, placement geometry, and observation evidence. Unknown geometry may be recorded as `unknown`, and completed gripper releases are labeled `released_unverified` until verified by observation. Bimanual handoff permissions and preferences remain governed by `airborne_handoff` and `handoff_preference`, with full dual-arm parallel execution preserved.

SO101 calibration controls and its offline SAM/LK/VGGT evidence tools have a [configuration ownership and precedence guide](so101-configuration.md), including the shared evidence JSON and explicit observation-derived VGGT support height.
