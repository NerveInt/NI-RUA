# Tool Registration, Execution Boundaries, and Extensions

The model catalog, live actor tool calls, and the program broker all read `ToolSpec` declarations from a single `ToolRegistry`. Adding a tool only requires registering its handler—without adding branches to `Harness.dispatch`, the Workbench allowlist, or the program allowlist. Existing declarations, public handlers, and legacy adapters live in `ni_rua/runtime/tools/definitions.py`, `handlers.py`, and `legacy.py`, respectively, while `builtins.py` assembles built-in tools into the runtime registry.

Each declaration contains `api_version` (defaulting to `"1.0"`), the input JSON Schema, `output_schemas`, the handler, allowed `roles`, the side-effect classification (`effect`), and an optional unavailability callback. `output_schemas` maps each permitted `ToolResponse.kind` to a JSON Schema validating its `data` payload; when a tool can return multiple result kinds, declare each `kind` explicitly rather than guessing types from display text. New `actor`/`program` plugins must provide this declaration explicitly. Registration validates the input schema, output schemas, and their root-level positive `examples`; invocation validates the actual typed result returned by the handler. Versions must follow `major.minor` format with a positive integer `major` and a non-negative integer `minor`.

Each `ToolSpec` corresponds to a Codex native function: the declaration must include `type="function"`, a string `name`, a string `description`, and `inputSchema`. Matching native `0.160` admission checks, `name` must be 1–128 ASCII letters, digits, `_`, or `-`, and must not start with `mcp` or `mcp__`. Legacy `namespace` / `exposeToContext` fields are rejected. The optional `deferLoading` field must be a boolean: omitting it or setting `false` publishes the tool directly, whereas `true` places it into the `ni_rua` namespace via the Codex adapter for on-demand discovery. The registry and program calls still use the original function name without introducing a second handler routing table. Root-level singleton `null` input schemas are also rejected by native admission. At registration time, the registry checks JSON representability across the entire declaration, these native fields, and known admission constraints before validating live inputs against the local JSON Schema; it does not impose Responses `strict` mode or MCP-specific fields. Because the native backend lowers and compacts input schemas, local schema validation does not claim that every JSON Schema keyword survives unchanged in the model request. Registration stores independent snapshots of the declaration, input/output/legacy schemas, and roles; mutating the original `ToolSpec`, the return values of `spec()` / `validate()`, the catalog, the manifest, or `_specs` inspection copies in the host will not alter the live contract. `validator_for()` likewise returns an independent validator without exposing shared mutable cached schemas. To change the behavior or declaration of a registered tool, build a new registry and corresponding session.

Parameter meanings, units, defaults, numerical bounds, and applicability conditions are part of the tool contract. Types and hard constraints belong in `inputSchema`, while field `description` strings explain domain semantics and invocation conditions. Public tools generate an input field guide inside the top-level `description` from the same input declaration, preserving field descriptions and constraints that native schema lowering might strip—without gating on a 5,000-byte size threshold. Note that for complex nested array items such as `robot_action.stages`, [`robot_action_schema.py`](../../ni_rua/runtime/actions/robot_action_schema.py) flattens top-level stage discovery properties so the serialized native `parameters` object stays below `codex-cli`'s 5,000-byte nested-array collapse threshold while enforcing full per-`kind` conditional `allOf` schemas at validation time. Conditional branches must state their applicability conditions rather than unconditionally merging `required` lists, types, or bounds from mutually exclusive branches. Examples are still published solely from their original example sources. Verify actual delivery field-by-field using loopback Responses tests against the real bundled `app-server` rather than assuming a field present in the Python catalog reaches the model.

The built-in tool declarations are not X5 constants. `public_definitions(profile=...)` renders camera and arm ids, the frame, the TCP name, clock wording, `robot_wait` rate and timeouts and the contact overlay from the run's `EmbodimentProfile` (`create_registry(runtime=harness)` passes `harness.embodiment`), and `robot_action_schema.build(profile)` generates the `robot_action` schema and its field guide the same way: every number in a description is read from the profile and a field the robot cannot honour is absent. `unified_actions` validates calls against the schema of the run's registry. A plugin must not type a camera, arm, frame, gripper number or TCP name that differs between robots: read it from `context.capabilities` (`arms`, `frame_id`, `tcp_config_id`, ...) at call time, and state units and defaults in its own description like any other field. A catalogue that differs per robot is still one frozen catalogue per run: an X5 run and an SO-101 run publish different `robot_action` schemas, and a native thread resumed against a changed catalogue is refused (`resume_tool_registry_conflict`). See [Embodiment Profile](embodiment-profile.md#model-visible-text-is-rendered-from-the-profile) and the per-robot catalogue regressions in `tests/test_embodiment_schema.py` and `tests/test_tool_descriptions.py`.

Formal geometry requests in `geometry_query` and measurement/target requests in `depth_query` publish their respective exact field types. The legacy RGB-D compatibility forwarding in `geometry_query` lists only the explicitly supported depth kinds and points to `depth_query` for the full contract rather than duplicating the depth parameter manual; compatibility payloads are still validated by the same `DepthRuntime` and cannot be used to pass arbitrary unknown kinds or bypass RGB-D availability checks.

The optional `value.gripper_relative` uses a measured TCP pose in the camera calibration's reference frame. For `arx-x5-link6-v1`, `grasp_position_m` remains the X5 pad centre (m). For `so101-gripper-frame-v1`, a measured named `gripper` joint angle is also required: `reference=cad_inner_fingertip_midpoint_at_measured_jaw` identifies the CAD midpoint of the swinging fingertips, not observed object contact. `fixed_tip_position_m` and `moving_tip_position_m` are their positions in the calibration reference frame (m); `opening_m` is their point-to-point distance (m). `jaw_midplane_normal` is the unit vector from moving to fixed tip for SO-101, not a claim that its faces are parallel. `point_minus_grasp_world_m` and `point_in_gripper_frame_m` are the first accepted point's displacement from the selected reference in world and tool axes (m), and `distance_from_grasp_m` is its norm (m). Unsupported TCPs or missing measured state omit this optional reference. SO-101 example: change measured jaw angle from 0 to 0.5 rad and the midpoint changes while the fixed tip remains fixed in TCP coordinates. See `test_so101_reference_uses_measured_swinging_jaw_and_tcp_rotation` in `tests/test_geometry.py`.

The `pixel_plane` branch of `geometry_query` accepts a single `observation_id`, `camera_id`, original-image pixel `pixel:[u,v]`, and required `plane_origin_m:[x,y,z]` and `plane_normal:[nx,ny,nz]`. It returns the conditional intersection `point_m` (`status=conditional`, not measured depth), the 3D sensitivity vector `d_point_d_normal_offset_m` for a +1 m offset along the plane normal, and cross-camera reprojections `cross_camera_projections` onto other calibrated cameras from the same frame. The optional `plane_origin_alt_m:[x,y,z]` computes a second intersection on a parallel plane with the same normal and returns `alternate_point_m`, `alternate_ray_distance_m`, and `assumption_delta_m`; the optional `target_camera_id` returns a projection overlay image on the target camera in the same call. Prefer `triangulate` when a feature is visible and matchable across two views; use `pixel_plane` when occluded in one view or when the target lies on a known support plane, verifying against cross-camera projections. When the absolute dot product between the ray and unit normal is less than `0.01`, or when the intersection lies at or behind the camera origin, the tool returns `unknown` with `value=null`. See `tests/test_geometry.py` for regressions.

Every projected pixel comes from `geometry.project` ([`ni_rua/robot/model/geometry.py`](../../ni_rua/robot/model/geometry.py)): `geometry_query` `pixels` and `tool_axes` (`project_points`, `project_geometry`, `preview_ee`), `pixel_plane` `cross_camera_projections` and `target_camera_id` `pixels`, `alignment` `projected_pixels`, `robot_contact_overlay` `points[].pixel_xy`, `focus_3d` sphere ROI back-projection (`project_sphere_to_camera`), and the trajectory, pose-axis and proxy overlays. A point is visible (`in_image=true`) only when it is in front of the camera, inside the range where the camera's OpenCV distortion model is monotonic, and inside the image. `distortion_monotonic_limit(D)` computes that range from the camera's own coefficients, without camera-specific constants: the first undistorted normalised radius `r = hypot(X/Z, Y/Z)` (= tan of the off-axis angle) at which `dr_d/dr` of the radial model `r (1 + k1 r^2 + k2 r^4 + k3 r^6) / (1 + k4 r^2 + k5 r^4 + k6 r^6)` reaches zero or its denominator vanishes. The tangential `p1, p2` and thin-prism `s1..s4` terms enter through their worst case over the azimuth (`6 r hypot(p1, p2) + 2 r hypot(s1, s3) + 4 r^3 hypot(s2, s4)` subtracted from `dr_d/dr`), so the limit is one conservative number per camera (cached); the sensor tilt does not fold and is ignored. Zero distortion has no limit, so X5/RoboDojo cameras with `D=0` are unchanged. Past the limit the fitted polynomial folds points back into the image, mirrored (SO-101: wrist camera beyond 52.0 deg off-axis, fixed camera beyond 50.2 deg). Such a point has no image location: its pixel is `null`, and so are values derived from it (`d_pixel_d_normal_offset_px`, an alignment `errors_px` entry, a triangulation `reprojection_error_px` entry); `in_image` is false; overlays draw nothing for it; a triangulated correspondence that reprojects there is `inconsistent_correspondence`; alignment leaves it out of `count`, `coverage` and the error statistics. Regressions: `tests/test_projection_validity.py`, with real SO-101 calibration numbers in `tests/fixtures/so101_projection_fold.json`.

When `features.object_table` and `features.persistent_object_tracking` are enabled, `geometry_query` also publishes `kind="reanchor_tracks"` ([`reanchor_tracks.py`](../../ni_rua/perception/external/reanchor_tracks.py)), accepting `observation_id`, optional `camera_id` (defaulting to the embodiment's overview camera, `"cam_head"` on ARX X5 / `"fixed"` on SO-101), `target_id` / `target_track_id`, `phrases` (`1..16` open-vocabulary noun phrases), `pos_pixels` / `neg_pixels` (`1..16` `[u, v]` pixel prompts in `px`), `reset` (default `false`), and `include_overlay` (default `false`, returning `0` images unless explicitly requested) to re-bind or reset persistent SAM 3.1 object tracks without advancing simulation (`effect="record"`). Likewise, `kind="scene3d"` accepts `include_wrist_views` (boolean, default `false`) to fuse calibrated wrist-camera points via measured joint FK and exposes `cavity_profile` in `queries` and [`scene3d_helpers.py`](../../ni_rua/perception/external/scene3d_helpers.py). For lossless local visual inspection without downscale-upscale blur, both `robot_observe` and `history_view_observation` accept `image_delivery` (`"none"`, `"focus_roi"`, `"head_only"`, `"all"`) and `focus_3d` (`target_m` `[x, y, z]` in the embodiment's calibrated frame in `m` and/or `object_id`, `radius_m` `0.02..0.40 m` default `0.08 m`, optional `cameras` `1..3`, `patch_px` `128..480 px` default `256 px`), back-projecting the 3D sphere through calibrated `K`/`D` (honoring `distortion_monotonic_limit(D)`) and live `T_world_camera` to 1:1 native-sensor crops and returning `crop_xywh_px = [crop_x, crop_y, w, h]` with exact coordinate recovery `full_uv = [crop_x + local_u, crop_y + local_v]` ([`focus_3d.py`](../../ni_rua/perception/focus_3d.py)). See [`tests/perception/external/test_focus_3d_roi.py`](../../tests/perception/external/test_focus_3d_roi.py) and [`tests/perception/external/test_pointcloud_field_and_reanchor.py`](../../tests/perception/external/test_pointcloud_field_and_reanchor.py).

The input guide is delivered as part of the tool definition itself, not as an extra system message or per-turn injected prompt. Twelve tools are directly visible: `task_plan`, `robot_action`, `robot_observe`, `program_run`, `operation_memory`, along with the frequently used `geometry_query`, `history_view_observation`, `robot_wait`, `robot_contact_overlay`, and `history_list_actions`, and the two read tools `robot_action_status` and `program_status`. Replies name those two as the read that returns what a reply left out (the `detail` entry, see [Tool Output Contract](tool-output-contract.md)), and a host whose tool search does not work cannot load a deferred tool, so they are not deferred. The remaining 8 built-in tools set `deferLoading=true` in their declarations and are loaded in full after discovery via native `tool_search`. The active catalog is still filtered by role and runtime configuration; deferred loading never re-exposes disabled or unavailable tools. Directly visible tools were selected based on primary model call frequency and case/task coverage in historical runs, with internal program calls counted separately. Because schemas returned by `tool_search` still undergo native simplification, on-demand loading does not replace description and constraint preservation. Tool search does not advance the physical environment, though it incurs tool interactions and follow-up model requests that count toward existing model request budgets. Invocations continue to check role, availability, input, and output through the same registry; native network tool restrictions remain unchanged, and no new search service or configuration toggle is introduced.

A frozen catalog supports native thread resume. Changing `deferLoading` counts as a catalog change, and the existing `resume_tool_registry_conflict` check rejects mismatched configurations before launch. Older flat-catalog threads can be resumed using their original catalog; a newer catalog must not be silently applied to an old thread. The current native SDK `thread/resume` RPC does not accept a parameter to replace `dynamicTools`.

`history_list_actions` accepts an optional `anchor="events"|"failures"|"gripper_commands"|"all"` to retrieve interaction slices from the current episode on demand. It returns a top-level summary (`selected_count`, `episode_action_total`, `status_counts`, `execution_issue_count`, `gripper_command_count`, `evidence_gap_count`, `next_start`) alongside compact interaction blocks (containing action identity, typed request/receipt evidence, `observation_ids.decision/execution_start/result`, `measured_delta` from execution start to result frame, gripper command positions, and explicit `evidence_gaps`), plus a `full_result` handle to read the raw request/receipt by action ID. Omitting `anchor` preserves the original paginated index and `detail="full"` complete-list semantics; `detail="full"` cannot be combined with `anchor` or pagination arguments. See [`history_output.py`](../../ni_rua/core/presentation/history_output.py) for the implementation and `test_history_output` / `test_tool_registry` for regressions.

This design follows patterns from [Codex's built-in shell tool](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/shell_spec.rs), where the parameter description for `yield_time_ms` explicitly states its default value, unit, and range—text that survives intact in live requests under our pinned version. Similarly, the [MCP SDK parameter description tests](https://github.com/modelcontextprotocol/python-sdk/blob/main/tests/server/mcpserver/test_parameter_descriptions.py) verify that `list_tools` parameter schemas preserve `description` fields, and its [constrained parameter tests](https://github.com/modelcontextprotocol/python-sdk/blob/main/tests/interaction/mcpserver/test_tools.py) generate both schemas and runtime validation from `ge`/`le` definitions. NI-RUA achieves the same guarantees from a single `ToolRegistry` and JSON Schema contract—serving Codex natively and publishing the exact same registry through `NI-RUAMcpServer` (`ni_rua/cortex/agents/mcp_server.py`) for `claude_code`, `opencode`, and `external` agents without duplicating schemas or swapping validation frameworks. For dynamic tool interfaces, see also the [app-server reference documentation](https://www.codex-docs.com/docs/app-server); where version differences exist, the pinned SDK and native loopback tests are authoritative.

`catalog(runtime)` and `invoke(..., role=...)` share the exact same availability check. At the entry boundary, `invoke` first rejects disabled or unauthorized tools, then performs full input schema validation and request-specific capability checks before calling the handler. Unknown parameters, booleans masquerading as numbers, and non-finite floats never reach a public handler. Underlying semantic owners remain responsible for cross-field constraints such as observation versions, native action budgets, and cached plan states. Native backends explicitly declare `unified_action.available`; legacy adapters lacking this field retain compatibility interpretation for `resampled` configurations. New backends must declare accurate capabilities and implement the corresponding ports rather than relying on omitted fields to imply validated support.

`ProgramRunner(harness.program_services())` receives only a frozen `ProgramServices` bundle: server-bound callbacks for tool validation, invocation, and `effect` lookup, observation snapshots, active-action query and cancellation callbacks, and the run's `Store`. The runner holds no direct reference to `Harness`, `robot`, or `ToolRegistry`. The `actor` role is bound by `Harness.handle_tool` and the `program` role by the server-side callback in `ProgramRunner`; callers cannot escalate their role via JSON arguments. `Harness.dispatch` serves as the `trusted_legacy` adapter entry point for existing Python integrations (legacy motion and `scene_*` tools were removed in the 2026-10 refactor). Legacy adapters retain their original semantic checks and cannot be used by actors or programs to bypass unified actions or primary-model review. The historical `from ni_rua.runtime.harness import TOOLS` compatibility alias was removed along with the legacy tools.

## Adding a Read-Only Tool

For existing opt-in plugins that read formal observations through narrow owner callbacks, see [Robotic View Solver](robotic-view.md) and [Stereo Epipolar Guide](stereo-guide.md); both reuse the same `actor`/`program` registry and deliver usage instructions through their respective `ToolSpec` definitions.

Place the declaration below under `ni_rua/runtime/tools/plugins/` (for example, `example_status.py`), import it at the application assembly point, and pass it to `Workbench(..., tool_specs=[make_status_tool()])` (hosts instantiating `Harness` directly also accept `tool_specs`). The handler receives a `ToolContext` whose read-only action port returns raw action records from the current run without exposing the robot instance or raw `Store`.

```python
from ni_rua.core.tool_output import ToolOutput
from ni_rua.runtime.tools.registry import ToolSpec


def make_status_tool():
    def read_status(context, arguments, correlation):
        # Fixed read-only port; does not grant arbitrary path, observer artifact, or database access.
        receipt = context.read_action(arguments["action_id"])["receipt"]
        return ToolOutput({
            "action_id": arguments["action_id"],
            "status": receipt["status"],
            "reason": receipt.get("reason"),
        }).response()

    return ToolSpec(
        definition={
            "type": "function",
            "name": "example_action_status",
            "description": "Read a saved action status without executing it.",
            "inputSchema": {
                "type": "object",
                "properties": {"action_id": {"type": "string", "minLength": 1}},
                "required": ["action_id"],
                "additionalProperties": False,
            },
        },
        handler=read_status,
        roles=frozenset({"actor", "program"}),
        effect="read",
        api_version="1.0",
        output_schemas={
            "data": {
                "type": "object",
                "properties": {
                    "action_id": {"type": "string", "minLength": 1},
                    "status": {"type": "string", "minLength": 1},
                    "reason": {"type": ["string", "null"]},
                },
                "required": ["action_id", "status", "reason"],
                "additionalProperties": False,
                "examples": [{
                    "action_id": "action-example",
                    "status": "completed",
                    "reason": None,
                }],
            },
        },
    )
```

Positive and negative output examples for this template can be checked directly with the same validator, and registration automatically validates `examples` without maintaining a separate example table:

```python
from ni_rua.runtime.tools.registry import ToolRegistry, validator_for

spec = make_status_tool()
ToolRegistry([spec])
check = validator_for(spec.output_schemas["data"])
assert check.is_valid({"action_id": "action-example", "status": "completed", "reason": None})
assert not check.is_valid({"action_id": "action-example", "status": True, "reason": None})
```

The `scene_` prefix is reserved for legacy adapters and cannot be registered as an `actor`/`program` plugin; registration rejects it immediately so the catalog never advertises a name that the entry point will refuse. Because `tool_specs` are added to the registry before `Harness` initialization, `features.disabled_tools` can reference plugin names, and duplicate names fail immediately. Workbench's runtime source archive recursively collects in-package Python files under relative package paths such as `runtime/tools/plugins/example_status.py` (with `Harness` archived under `runtime/harness.py`). The launch manifest's `tool_catalog` records the catalog hash, each tool's `api_version`, input schema hash, `result_kinds`, full `output_schemas` and their hashes, `effect`, availability, and unavailability reason. `api_version` is the author's explicit compatibility version for tool behavior and result semantics, whereas schema hashes identify structural shape—a behavioral change may require bumping `api_version` even when the schema is unchanged, so neither replaces the other. The catalog hash covers the delivered name, description, and input schema; the output contract hash is frozen separately without expanding Codex's input tool catalog. Older manifests lacking `api_version` or output contracts remain marked unknown rather than backfilled with current defaults. Source files from external packages are not automatically included in the NI-RUA package source archive and must be recorded separately by the host; keeping declarations shipped with the project inside the package is sufficient.

No module scanning, dynamic download/install, or separate plugin service is needed. For an existing `Harness` instance, you can also call `harness.tool_registry.register(spec)` explicitly before starting the actor session; registering tools after the session catalog has already been delivered will not dynamically update the client.

## Catalogue Profiles

`features.tool_catalog_profile` selects how each tool description states its input contract. The default is `layered_v3` (typed notation, rarely used fields shortened, the full lines in `tool_reference.md`); `full_v1` writes the prose field guide described below and restores the earlier catalogue. The default was evaluated in a small paired comparison on the simulated ARX-X5 with the Codex backend only (there is no full-benchmark-set evaluation and no task evidence for the other backends or the SO-101); the profiles are:

- `full_v1` / `guide_only_v1`: the prose field guide (`guide_only_v1` also omits, in Codex dynamic-tool schemas, property descriptions the guide already carries verbatim).

- `compact_v1`: the same contract in a typed notation, one line per field path (`stages[].max_upward_dz_m: number 0..0.15 -- ...`). Every field description, enum value, bound, default and conditional rule of the schema is kept.
- `layered_v1`: the typed notation, but fields named cold in [`catalog_guide.COLD`](../../ni_rua/runtime/tools/catalog_guide.py) are listed with path and signature (type, bounds, default) only, and the tools in `catalog_guide.COLD_TOOLS` are published with `deferLoading=true`. At startup the Workbench writes the complete lines of every cold field to `tool_reference.md` in the actor working directory (`catalog_guide.reference_document`).
- `layered_v2`: `layered_v1` with four differences. (1) A cold field's line keeps the start of its description (`catalog_guide.gist`): complete when it has at most `GIST_LIMIT` characters, otherwise cut at a word and ending in `...`. (2) Fields nested inside a cold field are not listed in the description, only in `tool_reference.md`. (3) The rule lines of rarely used forms of a union (`catalog_guide.COLD_FORMS`, the rarely used `geometry_query` request kinds) are replaced by one line naming those forms; their complete lines are in `tool_reference.md`. (4) `ToolRegistry.catalog(..., role="actor")` applies `catalog_guide.share_lines`: a field line that an earlier loaded tool of the published catalogue states identically (same path, text of at least `SHARED_MIN` characters) becomes `<path>: same as in <tool>`; tools published with `deferLoading` neither give nor take such references, so a reference never names a tool that is absent or not loaded. When the agent host loads deferred tools on demand, `Workbench.start` also appends `catalog_guide.on_demand_index` (one line per deferred tool) to the startup instructions.
- `layered_v3` (the default and the current layered form): `layered_v2` without its two mechanisms that did not work in evaluation. No tool is published with `deferLoading` beyond those the default catalogue already defers (in the evaluation runs no deferred tool was ever loaded: on the model channels used there the model's tool-search calls came back in a form the Codex host rejects as an unsupported call), hence no index of on-demand tools is added to the startup instructions; and the cold block describes `tool_reference.md` (one line per field, starting with the field path and a colon) instead of prescribing a shell command.

`layered_v1` and `layered_v2` are kept unchanged so that runs recorded with them load.

In every profile the guide is generated from the same input schema, and the schema, tool names, validation (actor and program roles) and results are identical; only the description text and `deferLoading` differ. A schema construct the typed notation cannot state faithfully (`catalog_guide.UnsupportedSchema`, for example an unknown keyword or field declarations inside a plain `anyOf` alternative) is published for that tool with the `full_v1` prose guide, so a description never differs from its schema. Cold fields and cold tools are an empirical, per-robot selection: they are explicit allow-lists applied only to the robot model with usage evidence (`catalog_guide.EVIDENCE_ROBOT`, currently ARX-X5), so any other robot, any new field and any plugin tool is described in full unless listed. With `agent.backend="external"` there is no NI-RUA-managed working directory, so a layered profile is published as `compact_v1`. A plugin tool needs nothing extra: all of its fields are described in each profile unless the tool is added to `catalog_guide.COLD`. `features.robot_urdf_delivery` (`file` by default, or `inline`) is independent of this: `file` puts the robot URDF text in `robot.urdf` in the same directory instead of the startup instructions, while `robot_information` still returns it; a session without a working directory (the external backend) gets it inline. For the SO-101 a layered profile gives the `compact_v1` text (with shared field lines) and writes no `tool_reference.md`; the URDF is delivered as the file.

## Side Effects and Program Authorization

`effect` can be either a fixed string or a callable returning a classification based on validated arguments. For `robot_action`, `preview` and `preflight` have effect `plan`, `inspect` has `read`, and `execute` / `direct` / `execute_if_clean` have `physical`. For `task_plan`, reading is `read` and saving is `record` (`geometry_query` with `kind="reanchor_tracks"` is likewise `record`, whereas pure geometry queries are `read`). Operational memory distinguishes `read`, intra-run `record`, and cross-task `shared_memory`. A sixth value, `session`, marks a call that changes only the agent-session bracket (no observation, plan, memory or physical effect): the `run_begin` and `run_finish` tools of the `external` agent backend ([`run_bracket.py`](../../ni_rua/runtime/tools/plugins/run_bracket.py), roles `{"actor"}`, registered only when `agent.backend="external"`, see [Agent Plugin](agent-plugin.md#the-bracket-run_begin-and-run_finish)). A transport that must tell call kinds apart before validation reads it through `ToolRegistry.effect_of(name, arguments)` ([`registry.py`](../../ni_rua/runtime/tools/registry.py)): it returns the static effect or the request-dependent one for these arguments, and never raises (an unknown tool, a non-object argument, a failing effect callable or a non-string verdict yields `None`, which a transport treats as an ordinary gated call), like `parallel_safe`. Names are never matched; no host tool declares `session`. Effect classifications describe domain side effects; routine logs or evidence artifacts created during read-only queries do not constitute physical actions.

`program_run` reviews physical actions by default. Built-in `robot_action` and `robot_wait` use the existing pause/resume review flow; additional program tools declared as `physical` can only execute if that `program_run` invocation was launched with `allow_direct_actions=true`—a plugin cannot bypass review simply by using a new tool name. Physical plugins requiring custom review workflows should initially expose only the `actor` role. `program_run`, `program_status`, and policy actions do not expose the `program` role, preventing programs from nesting sub-programs or escalating privileges through legacy entry points.

By default, plugins receive only `ToolContext` identity metadata, snapshots of current observation/capabilities/budgets, and `read_action`. Only `physical` invocations receive `execute(action)`, which forwards the broker correlation and assigns deterministic `action_id` values in call order within the tool invocation, routing actual execution through `Harness.execute` for state, budget, immutable payload, and idempotency checks. Neither the native `robot` backend nor raw database handles are exposed. Built-in history handlers explicitly bind their runtime dependencies at assembly time. Availability callbacks receive a separate frozen `ToolAvailability` containing only configuration, capability, and service-readiness facts.

Trusted Python code is still not a sandbox against malicious host code: additional services captured in closures by the host remain the host's responsibility. Plugins must faithfully honor their declared `effect` and never fabricate execution receipts; standard extensions should use the narrow read and execution ports described above.

## Internal Types and External Wire Replies

The external wire format remains `{success, contentItems}`. Internally, `ToolResponse` is a distinct non-mapping type holding `kind`, raw `data`, `success`, and separate `content` presentation items without implicitly serializing JSON on read. `ToolOutput(summary).response()` wraps `StructuredText(summary, projection="data")`. When presentation and execution facts differ, return `ToolResponse([StructuredText(display, "action_display"), ...], data=original, kind="action")` rather than substituting raw execution data for display text. Post-action observations are attached as separate content items, and program status vs. raw job records—or observation bundles vs. delivered metadata/images—are likewise stored separately.

Standard plugins default to `projection="data"` rather than guessing domain result types from JSON shape. At final actor delivery, valid IDs and artifact references are replaced with stable intra-run short references, and provenance is recursively stripped: hash/digest/checksum/fingerprint fields, source URLs/files/repositories/commits, document source sets, and hash-shaped `version` or `calibration_id` strings. Ordinary numeric revisions, `solver_version`, and similar domain values are preserved, and `image_url`/`audio_url` remain intact for media delivery. This filtering applies to both root and nested plugin fields, so plugins must not rely on filtered provenance fields to carry essential domain data to the actor. Program presentation and historical result replay apply the exact same filter, while typed `data` and raw observer archives retain all facts. Producers needing built-in summaries explicitly select named projections such as `capabilities`, `action_result`, `action_display`, `observation`, `operation_review`, or `contact_overlay`; `action_result` preserves the domain owner's full/summary structure without applying a second field-allowlist truncation to the receipt. Projection names govern presentation only and do not alter the trusted execution semantics of `ToolResponse.kind/data`.

Actor outputs are projected and serialized at the final delivery boundary in `ActorOutput.present`, while program file-descriptor replies apply the same metadata filtering and short-reference resolution in `ActorPresentation.present_response`. Artifact persistence of raw wire replies, logging, and explicit legacy calls generate plain JSON via `wire_response` / `wire_content`. `ToolOutput.content_items()` serves purely as an explicit wire-compatibility adapter. Reading historical wire/artifact/log records may retain legacy display cleanup, but those records must never be parsed backward to infer internal execution facts. Direct Python callers needing wire format should adapt explicitly rather than relying on internal dataclass serialization details.

Built-in tool output declarations first constrain existing result envelopes: `action` requires an object `receipt` with a string `receipt.status`, leaving full action, trajectory, execution counts, and state transitions to their domain owners; the registry neither duplicates a second physical contract nor re-infers whether execution completed. `plan` validates status fields and permits failed previews without a `plan_id`, while program review continues to require an executable cached plan. `observation` validates the bundle delivery envelope already verified by the shared observation contract. `history_list_actions` supports both paginated objects and full lists; `history_read_trace` preserves the archived JSON shape (which may be an array, scalar, or `null`), requiring only valid JSON without imposing extra structural restrictions on historical traces. Other `data` built-in results currently validate the top-level object container while leaving deep optional fields to their existing domain owners and regression suites; this container check does not claim that full field-level output schemas have been published for every legacy payload.

Display-only compatibility explicitly permits `null`: `history_view_observation` and `robot_contact_overlay` carry `data=None`, and action/trajectory inspection in `robot_action` may likewise return display items only with `data=None`. The broker never treats such responses as actions or fresh observation evidence. Other `robot_action` modes return `plan` or `action` and are validated against the corresponding `kind` schema. Only legacy adapters restricted exclusively to the `trusted_legacy` role may set `output_schemas=None` (recorded in the manifest as `trusted_legacy_wire_unvalidated`); new `actor`/`program` plugins cannot use this exemption.

An output contract violation occurs after the handler has already returned. Rather than raising an input error, the registry preserves the original `kind/data` and serializable display items, returns `success=false`, and appends an `output_contract_error` with `phase=after_handler` and an instruction forbidding automatic replay. Persisted `completed`, `partial`, or `stopped` receipts remain intact; execution outcome is `unknown` only when a trusted typed receipt is missing. The program broker increments its output-error counter while still recording actual execution facts from the original receipt. Here, `success=false` indicates a response contract failure, not that the physical action failed to execute. Non-JSON values or display items violating native content-item shapes are quarantined while valid items are still delivered, without calling `repr()` on invalid objects or replaying the action; `action` responses also attach a serializable summary of the typed receipt facts. Content items must be `StructuredText` or native `inputText/text:string`, `inputImage/imageUrl:string`, or `inputAudio/audioUrl:string` items—arbitrary JSON scalars or objects are not valid native content items. Malformed native items report `invalid_native_content_item` with the exact `/content/<index>/<field>` pointer, and any other output error also strips invalid items. Actor projection failures preserve the same post-execution error semantics. Outer `success` must be a true boolean; integers, strings, `None`, or non-JSON objects produce a `/success` after-handler diagnostic rather than downgrading a response-contract error into execution `unknown`. The registry validates outer types, JSON representability, native content items, and declared schemas before generating JSON text.

When a handler assembles optional observations, images, or detail artifacts after physical execution has already occurred, it must also guard against delivery exceptions: preserve the typed `action` facts first, then reuse `output_contract_error` to return `action_feedback_unavailable` so an exception never turns into a receipt-less generic tool failure. The unified action, wait, and policy handlers all cover this path. Idempotent replay of an older checkpoint must not write historical revisions or cursors back into the active plan.

The program broker's review flow, action summary, and latest observation tracking read cached plans from `kind="plan"`, raw `{receipt, ...}` payloads from `kind="action"`, and `ObservationBundle` instances from `kind="observation"`. It never parses `inputText` to recover internal execution facts; corrupted display text, field compaction, or spoofed `stdout` cannot alter trusted state. If only an external wire dict is present without an internal action result, execution counts and outcomes remain `unknown`—never backfilled with zeros or upgraded to success. Action IDs are taken from the receipt first and fall back to the original request if omitted, never parsed from display text. Full wire replies are still saved as observer artifacts for replay, not as unfiltered fallbacks readable by the actor.

See `tests/test_tool_registry.py` for regressions covering: invoking new read-only tools from both the live actor entry point and isolated Python programs; zero handler/action side effects on invalid input; output schema declarations and positive/negative examples; output schema hashes; preserving original receipts without replay when output violations occur after action completion; keeping missing receipts as `unknown`; configuration/profile/backend availability matrices; verifying spoofed display text cannot alter broker evidence; and recursive source archiving. `tests/test_program_review.py` additionally covers live process pausing, review, cache invalidation on world advancement, and unknown execution outcomes.

Targeted regressions in `tests/test_typed_actor_output.py` also verify: internal presentation without premature serialization or parsing, named mixed replies, domain field preservation alongside recursive actor provenance filtering, metadata fallback synchronization, post-execution display failures, and post-save program replay.

Context budget is a first-class interface constraint: non-essential metadata should be omitted at the producer. The presentation layer also strips hash fields, unnamed bare hashes, and checksum fragments in free text without inserting verbose placeholder text. Essential `action`, `job`, `review`, `observation`, `plan`, and `artifact` IDs use stable short references from the same `Store`—including composite IDs, dictionary keys, and references in program source code—and are resolved back to original identities at both entry boundaries. Bare hashes extracted via JSON Pointer, `stdout`/`stderr`, error strings, and text artifacts follow the same rules, while image and audio bytes are preserved unchanged. Output schema properties and `required` lists must not be broken by field filtering; hash-shaped enums that must be round-tripped use reversible short references while internal validation continues to check original values.

At the program execution entry point, only necessary object references in source code are normalized to the short references used in tool replies so source literals and tool responses can be compared directly; free-text scrubbing is never applied to executable source code. Ordinary code, checksum literals, and numeric constants remain untouched, idempotency checks use original call arguments, and the source archive records the exact executed code. See `tests/test_tool_registry.py` for live `program_run` reference, source, and replay regressions.

Auxiliary visual review filters structured evidence before serialization, and `CodexSession` filters readable text again on outgoing `/responses` and `/responses/compact` requests, covering resumed history. Native call/item IDs, media URLs/data, and encrypted reasoning tokens retain their exact protocol values without being expanded as display text. Internal verification hashes, idempotency digests, and provenance audits are never deleted by presentation rules. Tests should capture actual loopback HTTP or helper-turn payloads rather than only testing a standalone formatting helper.

## Structured Results for Generated Programs

`NiRuaClient.call()` returns `success`, `kind`, `data`, and compatibility display `contentItems`. Generated programs consume `data` keyed by `kind`: action receipts live at `data.receipt`, while plans and planning rejections live in `data` under `kind="plan"`. `ToolOutput.projection` selects the domain data projection simultaneously; producers constructing `ToolResponse` directly use `data_projection` to explicitly select the corresponding metadata projection rather than guessing from display text or tool names. Everything then passes through `ActorPresentation` for metadata filtering and short-reference resolution. Public output `data` must still obey observation permissions and output schemas, and must never expose hidden internal state.

`kind="untyped", data=null` preserves the uncertainty of legacy display-only results, while `kind="error"` on exceptions reports invocation diagnostics only without inferring whether physical execution occurred. An `output_contract_error` on an already executed action does not alter the original receipt and must not trigger a resend. Idempotent replay of cached legacy results does not parse text to fabricate domain facts. For examples and regressions, see [Program Result Semantics](program-result-semantics.md), `tests/test_program_review.py`, and `tests/test_actor_presentation.py`.
